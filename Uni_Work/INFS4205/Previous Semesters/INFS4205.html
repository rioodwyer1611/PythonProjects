1. Multimodal Embedding — The Transformer

The story starts with a problem. Raw data lives in very high dimensional spaces. A modest 220 by 160 colour image already has about 105,600 dimensions if you count every pixel and channel. Euclidean distance in that raw space is almost meaningless because the volume of the space grows so fast that all points end up roughly equidistant from each other. This is what the course calls the curse of dimensionality, and the way out of it is the manifold hypothesis: real data does not fill the entire high dimensional cube uniformly, it sits on a much lower dimensional surface called a manifold. Our job is to learn a function f(x) that maps raw input onto that manifold so that distances become meaningful again.

Why Hand-Crafted Features Hit a Wall

Before deep learning, practitioners reached for global statistics. For images you would compute colour histograms, which are invariant to scaling and rotation but throw away all spatial information. For text the equivalent was Bag of Words, which counts how often each word appears regardless of order. Bag of Words has a famous failure mode: the sentences "Dog bites man" and "Man bites dog" produce identical vectors because BoW ignores syntax and position. The vectors are also enormous and sparse, since you need one dimension per word in the vocabulary, and meaning collapses without context.

A second wave of features added local structure. HOG and SIFT for images capture local gradient orientations and edge contours instead of just raw colour, and n-grams for text capture short word sequences such as "not good" versus "good". These methods made a strong locality assumption (only nearby pixels or nearby words matter) and were still hand designed. The cost of n-grams in particular grows as V to the n, where V is vocabulary size and n is the window length, so the representations stayed sparse and brittle.

The Transformer as Universal Encoder

The Transformer architecture, introduced in 2017, became the universal feature encoder across text, vision, and other modalities. From a high level it follows an encoder-decoder pattern. The encoder reads the input and produces a representation, the decoder consumes that representation and emits an output one token at a time. When you generate text, the model is autoregressive, meaning at step t it conditions on everything it has already produced. Modern systems built on this idea include GPT, Claude, Gemini, and Llama.

If you zoom into the encoder, you see four stages stacked together: tokenization turns the input into a sequence of discrete units, positional encoding tells the model where each token sits in the sequence, self-attention lets every token look at every other token, and an output projection turns the final hidden state back into something useful such as a probability distribution over the vocabulary.

Tokenization in Depth

Tokenization breaks raw text into a sequence of discrete units the model can look up in an embedding table. The naive approach is word level (one token per word), but the vocabulary becomes enormous and you cannot handle unseen words. Character level fixes the vocabulary problem but makes sequences extremely long, which hurts attention cost. The compromise that became standard is subword tokenization, and the algorithm of choice is Byte-Pair Encoding (BPE).

BPE starts with a base vocabulary of individual characters or bytes, then iteratively finds the most frequent adjacent pair in the training corpus and merges it into a new token. After many merges you end up with a vocabulary that contains common whole words, common prefixes and suffixes, and individual characters for rare cases. The word "unbelievable" might become four tokens [un, bel, iev, able] in a smaller vocabulary such as Llama 2 (32K tokens) or three tokens [un, bel, ievable] in a larger one such as Llama 3 (128K tokens).

To handle multilingual text and unusual symbols, modern systems use byte-level BPE. Every character is first encoded as a sequence of UTF-8 bytes, so the base vocabulary is exactly 256 entries. This guarantees you can represent any string from any language, but the cost is that languages outside English may need more tokens per word, which raises compute. The tutorial walks through this with Llama 2 versus Llama 3: a larger vocabulary lets each token carry more meaning, so sequences are shorter, attention is cheaper (because attention cost scales quadratically with sequence length), but the embedding matrix and output projection both grow linearly with vocabulary size.

Vocabulary Size Trade-Off Worked Example

Llama 2 uses 32K vocab, Llama 3 uses 128K. With d_model = 4K, the extra vocabulary adds 96K times 4K times 2 (embedding plus output head) which is about 768M parameters. That is roughly why Llama 3 is marketed as 8B versus Llama 2 at 7B. The benefit is a shorter sequence for the same text (about 15 percent shorter), which makes the quadratic attention cost drop by roughly 28 percent because 0.85 squared is about 0.72. The downside is that the final softmax has to normalise over 128K classes instead of 32K, so single token generation at the output layer is slower on Llama 3.

Embedding Lookups and Permutation Invariance

Once you have token IDs, you look them up in an embedding table to get a vector of dimension d_model for each token. The whole sequence becomes a tensor of shape (sequence length, d_model). When you have many sequences in a batch with different lengths, you pad the shorter ones to a fixed length and use an attention mask so the model ignores padding positions.

Crucially, the embeddings on their own are permutation invariant. If you shuffle the tokens in the sentence "dog bites man" to "man bites dog", the set of embedding vectors is identical, and self-attention with no positional information would give the same output. That is unacceptable for any language or sequence task, which is why we add positional encoding.

Positional Encoding

There are two main families. Absolute Positional Embedding learns a vector for every position up to some maximum, but this has an extrapolation problem: if you train on sequences up to length 2048, you cannot reliably handle a length 4096 sequence at inference because positions 2049 through 4096 have no learned embedding. Sinusoidal positional encoding solves this by using fixed mathematical functions instead of learned vectors. The pattern is:

$$PE(pos, 2i) = \sin\!\left(\frac{pos}{10000^{2i/d}}\right) \qquad PE(pos, 2i+1) = \cos\!\left(\frac{pos}{10000^{2i/d}}\right)$$

Even dimension indices use sine, odd indices use cosine, and each pair of dimensions uses a different frequency. Lower indices oscillate slowly, higher indices oscillate quickly. This is a bit like reading a clock at multiple time scales at once. A particular position pos becomes a vector such as [0.84, 0.54, 0.01, 1.00] for d=4 at pos=2.

The clever property is that a shift of k positions can be expressed as a linear transformation (a rotation) of the original encoding. That makes relative position information emerge automatically from the attention scores. Rotary Position Embedding (RoPE) takes this idea further by literally rotating pairs of dimensions in the query and key vectors based on their position. RoPE has become the default in models like Llama and Qwen because it extrapolates better to longer sequences than absolute embeddings.

Self-Attention

Self-attention is the workhorse. Each input token x_i is projected into three vectors using three learned matrices: a query Q = xW_Q, a key K = xW_K, and a value V = xW_V. The intuition is that the query asks a question, the keys advertise what each token has to offer, and the values are the content to be aggregated. The attention computation is:

$$\text{Attention}(Q, K, V) = \text{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}\right) V$$

The dot product between query i and key j produces a score that measures how relevant token j is to token i. We divide by the square root of d_k to keep gradients stable, since dot products of high dimensional vectors can blow up. Softmax normalises the scores into a probability distribution, then we use those probabilities to take a weighted sum of the value vectors. The model "routes" content from the most relevant context (V) into the current position. The attention weights themselves are interpretable: you can visualise which tokens attend to which.

Multi-head attention runs several attention operations in parallel, each with its own Q, K, and V projections, and concatenates the results. Each head can learn a different pattern: one might focus on syntactic dependencies, another on semantic similarity, another on positional structure. The trade-off is redundancy. Models are heavily overparameterised, and pruning studies show many heads learn duplicate or useless patterns, so called "dead heads".

The Feed-Forward Network and Residuals

Around the attention block sits a feed-forward network (FFN) and residual connections. The FFN is a simple two-layer MLP that first expands from d to 4d, applies a non-linearity (such as ReLU or GELU), and then projects back down to d. The expansion creates a richer non-linear basis for the model to work with. The parameter cost of one FFN is 8d squared, which exceeds the 4d squared cost of all four attention projection matrices combined, so most of the compute in a Transformer lives in the FFN.

Residual connections add the input of each sublayer to its output, which keeps gradients flowing through deep stacks. LayerNorm normalises across the feature dimension to stabilise training. Modern Transformers use pre-norm (LayerNorm before the sublayer, then residual add) rather than post-norm (sublayer first, then LayerNorm) because pre-norm gradients are more stable at depth.

KV Cache and Autoregressive Decoding

When you generate text one token at a time, naive decoding wastes a lot of compute. To generate token t you would in principle feed the entire prefix [x_1, ..., x_{t-1}] through every Transformer layer to recompute keys and values. But those keys and values do not change once computed, so you can cache them. This trick is called the KV cache and is the cornerstone of fast inference.

The new step looks like this: generate Q_{t-1}, K_{t-1}, V_{t-1} for the new token, retrieve cached K_{<t-1} and V_{<t-1}, concatenate to form the full K and V, compute attention with the new query against the full cached K and V, and store the new K_{t-1} and V_{t-1} in the cache for next step. The benefit is that you only ever process one new token per step at all but the attention layer, which makes generation essentially linear in sequence length per token at the FFN level.

The cost is memory. The KV cache size in bytes is:

$$\text{KV}_{\text{size}} = \text{batch} \times 2 \times L_{\text{seq}} \times N_{\text{layers}} \times d_{\text{model}} \times \text{bytes}$$

For a typical 128K context model with 32 layers, d_model = 4K, FP16, and batch size 1, this works out to 1 × 2 × 128K × 32 × 4K × 2 = 65,536 MiB = 64 GiB. That is the entire KV cache memory before you even load the model weights. This is exactly why models impose hard context window limits. Without one, conversation length grows the cache until it exhausts GPU memory, attention becomes slower because each new query must attend to all previous keys, and inference latency spirals. When you exceed the limit, systems either silently drop the oldest tokens or fail with a "conversation too long" message.

Why Context Windows Exist

Common context windows: 4K (GPT-3.5, Llama 2), 32K (GPT-4-32k, Yi-34B), 128K (GPT-4o, Llama 3.1, Qwen2, DeepSeek-R1), 200K+ (Claude 3/4 Sonnet, Yi-34B 200K), 1M (Gemini Pro/3, Claude 4 beta, GPT-4.1), and 10M+ (Llama 4 Scout, Magic). The limits exist because of hardware constraints, mostly KV cache memory growing linearly with sequence length and attention cost scaling with O(L) per new token even with the cache.

Vision Transformer (ViT)

The Transformer was originally a text architecture. To apply it to images, ViT splits the image into patches, treats each patch as a token, and feeds them into a standard Transformer encoder. For a 224 by 224 image with patch size 16, you get 14 by 14 = 196 patch tokens. Each patch is flattened from 16 by 16 by 3 = 768 pixel values and then linearly projected into a d-dimensional embedding. Common sizes are ViT-B/16 with d = 768, ViT-L/16 with d = 1024, and ViT-H/14 with d = 1280.

ViT prepends a learnable [CLS] token to the patch sequence. The [CLS] embedding gets transformed by self-attention along with the patch tokens, and its final state is used as a global summary of the image for classification. The role of [CLS] is to aggregate global image information for the classification head, exactly as it did in BERT for text.

Positional encoding for ViT is typically a learned 1D embedding for the patch grid, sometimes a 2D embedding that factorises into row and column components. The model has to learn locality from data because, unlike a CNN, it has no built-in inductive bias that nearby pixels are related. This is why ViT needs much more data than a CNN to reach the same accuracy. Convolutions bring locality and weight sharing for free, but Transformers have to learn both from a very large dataset.

The architecture has been extended to detection (DETR uses a Transformer decoder that predicts a fixed set of object queries), to multimodal tasks (CLIP, BLIP-2, LLaVA, covered later), and to many other vision problems.

2. Self-Supervised Multimodal Embedding

The previous topic ended with ViT needing enormous amounts of data. This topic is the answer to that problem. We will see why scaling matters, why labels are the bottleneck, and how self-supervised learning sidesteps the need for human annotation entirely.

Scaling Laws

Empirically, model performance follows a power law in the size of the model (N), the dataset (D), and the compute (C). As you scale these up, prediction error keeps falling but the rate of improvement slows down. To reduce error linearly by a small amount you typically need to increase compute exponentially. This means scaling alone is not free, it is expensive, and the cost compounds.

Two influential papers laid out the trade-off. Kaplan et al. argued that model size N should grow faster than dataset size D for a given compute budget. Hoffmann et al. revised this with the Chinchilla finding: for a 10× compute increase, you should actually grow both N and D, more balanced than Kaplan suggested. GPT-3 had N = 175B and D = 300B, which Chinchilla suggests was undertrained, so newer models prioritise more tokens.

Scaling unlocked emergent capacities, where capabilities such as multi-step reasoning, code generation, and in-context learning suddenly appear once a model crosses a size threshold. The same emergence phenomenon is hoped for in vision, but vision faces a fundamental limit: vision labels are sparse. A whole image gets one classification label, whereas a text token sequence gets dense next-token supervision at every position. To scale ViT, we need denser learning signals, which is where self-supervised learning enters.

What Limits Scaling Today

Major bottlenecks include exhausted high-quality human-generated training data, exponentially increasing GPU and electricity cost for only linear gains, performance decay from training on AI-generated synthetic data, and structural problems such as logical hallucinations that scaling alone does not solve.

Self-Supervised Learning (SSL)

SSL is a form of representation learning that creates its own labels from the data itself. Supervised learning is Y = f(X) with X and Y both provided. Self-supervised learning is either X_i = f(X_i), where part of the data is hidden and the model predicts it from the rest, or X_j = f(X_i), where the model predicts the relationship between two samples. Yann LeCun once described SSL as the cake, supervised learning as the icing, and reinforcement learning as the cherry on top, by which he meant SSL is where most of the signal comes from when you train at scale.

Self-Prediction Pretext Tasks

The first family of SSL methods is self-prediction: hide part of the data and ask the model to predict it. Early pretext tasks were hand designed. Predicting image rotation forces the model to learn a "visual commonsense" of what an object should look like unperturbed. Predicting the spatial layout of patches (the jigsaw puzzle task) forces the model to ignore low-level colour or texture statistics and reason about relative location. These tasks worked but did not scale, because they were task-specific, often too easy or too hard, and prone to shortcuts (the model finds a clever way to solve the pretext task without learning anything useful).

The breakthrough was Masked Autoencoders (MAE) by He et al. MAE randomly masks 75 percent of image patches, encodes only the visible 25 percent through a ViT, then a small decoder reconstructs the missing patches from those visible features. The loss is mean squared error between predicted and actual pixels. The high masking ratio is critical because it prevents trivial solutions: with 75 percent masked, the model cannot just interpolate from neighbours, it has to reason globally. Random masking works better than block masking because it leaves a more even spread of information. MAE generalises to audio (MAE-AST listens to spectrograms with the same recipe).

Contrastive Learning

The second family is contrastive learning: predict the relationship between samples. You take an image x, apply two random augmentations to get x_1 and x_2, and force their embeddings close together while pushing them away from all other images in the batch. Augmentations include random crops, colour jitter, Gaussian blur, horizontal flip, and random grayscale. The mathematical loss is the InfoNCE loss, which is cross-entropy over the cosine similarities between one positive pair and N-1 negatives:

$$\mathcal{L} = -\log \frac{\exp\!\bigl(\text{sim}(z_i, z_j) / \tau\bigr)}{\sum_k \exp\!\bigl(\text{sim}(z_i, z_k) / \tau\bigr)}$$

SimCLR is the canonical version. It uses cosine similarity as the score function, adds a projection head (MLP) on top of the encoder for the contrastive loss but discards it for downstream tasks, generates positive pairs through augmentation, and uses every other sample in the batch as negatives. The temperature τ scales the similarity logits before softmax, and it matters a lot. A low τ makes the distribution sharp and forces the model to focus on the most similar pairs, a high τ makes it smooth. Setting τ too extreme hurts gradient flow, so CLIP and similar models make τ a learnable parameter, usually initialised near 0.07.

Contrastive learning needs lots of negatives. With too few, the model lazily collapses everything to a local area in embedding space, a degenerate trivial solution. SimCLR addresses this with very large batch sizes, often in the thousands, which is expensive. Momentum Contrast (MoCo) solves the same problem cheaply by maintaining a FIFO queue of past encoded samples to act as negatives. The momentum encoder is a slowly updated copy of the main encoder (the queue) with stop-gradient, so the negatives are consistent across training steps.

DINO: Self-Distillation with No Labels

DINO took the teacher-student idea further and removed explicit negatives entirely. Both networks are identical ViTs with a 3-layer MLP projection head producing an N-dimensional output (default N = 65536 prototypes). Both receive augmented views of the same image. The student takes both global and local crops, the teacher only takes global crops. This "local to global" design forces the student to deduce the teacher's holistic representation even from small local patches. The student is updated with cross-entropy loss against the teacher's prediction. The teacher is updated with an exponential moving average of the student weights: Θ_t = l × Θ_t + (1-l) × Θ_s, with l typically 0.99.

Two tricks prevent feature collapse. Centering subtracts a running mean from the teacher's output to stop any single prototype from dominating across all images. Sharpening uses a lower temperature for the teacher than the student, which forces the student to mimic a peaky, high-confidence target. Centering encourages diversity, sharpening encourages confidence, and the two together balance into useful representations. Stop-gradient is applied only at the teacher branch, so gradients flow through the student during backprop.

The teacher is not updated by gradients because if it changed as fast as the student, the target would be a moving goalpost and training would diverge. EMA also acts as a temporal ensemble, aggregating the student across many iterations to produce more robust predictions.

DINO versus MAE

DINO and MAE both produce strong features but they differ in what those features are good for. DINO produces more universal patch representations, MAE embeddings have higher variance components which hurts distance-based tasks such as k-NN or clustering. DINO features work better for downstream tasks without finetuning. Modern segmentation foundation models such as Segment Anything (SAM) build on DINO features for their backbone. MAE on the other hand gives excellent localisation and counting because reconstruction forces the model to encode dense spatial information.

I-JEPA

I-JEPA combines DINO and MAE. Instead of reconstructing pixels (MAE) or matching crops (DINO), the model masks a target block of patches and learns to predict the latent representation of that block from the visible context. The loss is applied in embedding space, not pixel space, so the model does not waste capacity on low-level pixel details. Mask tokens (positional encodings) tell the predictor what to predict. This is closer to how humans think: we predict abstract states, not specific pixels.

3. Multimodal Alignment

Now we have strong vision encoders and strong language encoders, but they speak different languages. Multimodal alignment is the question of how to learn a shared representation between modalities so that the system can do retrieval, zero-shot classification, captioning, and visual reasoning. Zero-shot prediction is the ability to make predictions on a new task or class without seeing any labeled examples of that task during training. CLIP made this concrete for image and text.

Families of Vision-Language Models (VLMs)

The course frames VLMs in four families that map cleanly to a historical progression:

  • Two-tower, alignment only: CLIP (OpenAI, 2021). Separate image and text encoders projected into a shared space, trained with contrastive loss.
  • Two-tower, alignment plus text decoder: CoCa (Google, 2022). CLIP-style alignment plus a captioning head, so the model can also generate text.
  • Two-leg, Q-Former plus frozen LLM: BLIP-2 (Salesforce, 2023). A trainable bridge module called the Q-Former connects a frozen image encoder to a frozen LLM.
  • Two-leg, MLP plus frozen LLM: LLaVA (Microsoft/UW, 2023). Even simpler: a single MLP projects image features into the LLM's token space.

CLIP (Contrastive Language-Image Pretraining)

CLIP applies the SimCLR idea to image-text pairs scraped from the web. The model has two encoders, one for images and one for text. Each encoder produces a single vector, the [CLS] token from a ViT for the image and the final hidden state of the EOS token for the text. The two vectors are normalised, and a symmetric contrastive loss is applied: image-to-text and text-to-image. For a batch of N image-text pairs, the loss maximises the cosine similarity of the N diagonal (matched) pairs and minimises the N times (N-1) off-diagonal (mismatched) pairs. The training data was WebImageText, 400M image-text pairs harvested from the web with their alt-text as captions.

The result is a shared image-text embedding space where matched pairs end up close together. To do zero-shot classification on a new dataset, you do not retrain anything. Instead you turn each class name into a prompt such as "a photo of a {class}", encode it with the text encoder, then compute cosine similarities between the image embedding and each class embedding. The argmax gives the predicted class. The text encoder essentially becomes a runtime classifier that you can reconfigure for any vocabulary just by writing text prompts.

Why Prompt Engineering Matters for CLIP

CLIP class labels live as text embeddings in a shared image-text space. The text prompt you choose changes the embedding and therefore changes the similarity score. "a photo of a dog" works better than just "dog" because CLIP was trained on natural language captions. Common strategies are: make prompts resemble natural captions, average multiple prompts to reduce single-wording bias, include attribute and scene details for specificity, and adapt prompts to the target domain. CLIP often fails on negation ("a girl wearing a dress that is not blue"), attribute binding ("a boy in black and a girl in white" versus "a girl in white and a boy in black"), and relational reasoning ("a dog chasing a man" versus "a man chasing a dog") because it relies on similarity matching and co-occurrence statistics, not deep linguistic understanding.

The largest CLIP model is ViT-L/14 at 336 pixels, which significantly outperforms smaller variants on linear probe transfer. Ensembling multiple prompts at inference improves zero-shot accuracy further. CoOp (Context Optimization) takes the next step by replacing the manual prompt with learnable context tokens; only those tokens are updated, the rest of the CLIP weights stay frozen.

CLIP opened the door to open-vocabulary detection and segmentation. MaskCLIP and RegionCLIP modify the attention pooling to extract dense pixel-level features without needing a fixed set of labels. CLIP also powers DALL-E 2 and other text-to-image diffusion models, which rely on the joint image-text embedding to condition image generation on text.

CoCa: Adding Generation

CoCa is a two-tower model that unifies contrastive alignment with captioning. The image encoder feeds into two attention pooling modules. The first uses a single learnable query to aggregate the patch features into one global embedding for contrastive loss with the text encoder. The second uses 256 learnable queries to aggregate the patch features into a 256-token sequence that feeds into a text decoder, which generates captions in an autoregressive way. So the same image encoder serves two losses: contrastive (for alignment) and captioning (for generation).

For multimodal understanding tasks such as visual question answering, you train a classifier on top of the decoder. Learning to caption helps zero-shot classification and text-to-image retrieval, because captioning forces the model to learn richer language priors than contrastive alone. CoCa scaled up using JFT-3B (with label names as text) and ALIGN (over 1B web-crawled noisy alt-text pairs).

BLIP-2: Bridging Pretrained Models

CoCa is strong but expensive because everything is trained jointly. BLIP-2 asks a clever question: can we reuse a pretrained image encoder and a pretrained text decoder, and just train a small bridge module between them? The answer is yes. The bridge is called the Q-Former.

The Q-Former takes 32 learnable queries (M=32, d=768) and uses cross-attention against the frozen ViT output (typically 257 tokens of dimension 1024) to produce 32 summary embeddings. So the visual side is compressed from 257 by 1024 to 32 by 768, which is much smaller than the original ViT output. Training has two stages. Stage 1 trains the Q-Former alone with three objectives: image-text contrastive loss, image-grounded text generation, and image-text matching. Different attention masks let the text branch behave as a multimodal encoder, autoregressive decoder, or unimodal encoder for these losses. Stage 2 freezes the Q-Former and the LLM, and trains a small projection that converts Q-Former outputs into LLM-compatible token embeddings. Total trainable parameters are about 100M, which is tiny by modern standards.

LLaVA: Visual Instruction Tuning

LLaVA is even simpler. The architecture is a pretrained CLIP image encoder feeding into a single MLP projection, whose output is concatenated with text token embeddings and fed into a pretrained LLM such as Vicuna. The connector is just two-leg: a tiny MLP, not a Q-Former. Training has two stages. Stage 1 (image-caption pretraining) trains only the MLP projection to align image features with text. Stage 2 (instruction tuning) trains the projection and the LLM jointly on instruction-following data.

The breakthrough in LLaVA was not the architecture but the data. Public multimodal datasets are mostly image-caption pairs which are dry. LLaVA used GPT-4 (text-only at the time) to bootstrap instruction-following training data. They fed GPT-4 a structured caption plus bounding boxes for each image, then prompted it with a system prompt to generate three kinds of data: conversational dialogue, detailed description, and complex reasoning question-answer pairs. The result was a dataset of 158K instruction-following multimodal samples.

LLaVA 1.5

LLaVA 1.5 made three changes. First, the prompt was formatted more carefully so that specific question types got specific answer formats ("answer the question using a single word or phrase" for VQAv2, "answer with the option letter" for multiple choice). Second, the connector became a two-layer MLP with GELU activation, going 1024 to 4096 to 4096. Third, the training set grew to 665K samples by adding OCRVQA (text-heavy images), OKVQA (knowledge-based questions), GQA, and ShareGPT (multilingual coverage). These changes turned LLaVA from a strong conversational model that fell short on traditional VQA benchmarks into a general-purpose visual assistant with strong scores across the board.

LLaVA 1.5-HD and LLaVA-Next

Resolution became the next bottleneck. CLIP ViT-L was trained at 224 by 224, but high-resolution understanding (charts, dense text, small objects) needs more pixels. LLaVA 1.5-HD splits a 448 by 448 image into four 224 by 224 tiles, encodes each separately, and also encodes a resized full image as a global view. A special row-end token tells the LLM which tile sits where. Scaling resolution alleviates hallucinations because the model can see fine detail. But going too high hurts OCR and small object understanding, because attention spreads thin.

LLaVA-Next (LLaVA 1.6) preserves native aspect ratios by choosing from a set of grid layouts: 336 by [(2,2), (1,2), (2,1), (1,3), (3,1), (1,4), (4,1)]. This avoids wasting computation on padding for portrait or landscape images. LLaVA-UHD dynamically selects the best-match partition and uses a Q-Former-like compression to save compute. The improvement on OCR tasks is significant even without new training data.

Qwen2-VL and M-RoPE

Qwen2-VL took a different approach. The LLaVA paradigm has information redundancy and spatial collapse, because forcing a 2D image into a 1D token sequence with absolute position embeddings loses too much spatial structure. Qwen2-VL introduces M-RoPE (Multimodal Rotary Position Embedding), which factorises position into three dimensions: time, height, and width. Each dimension gets its own RoPE rotation. This lets the model extrapolate to longer sequences during inference and handle variable-length inputs natively, including videos with multiple frames over time.

Open Question: Visual Reasoning

Recent research has pushed in two directions. First, multimodal in-context learning: give the model a few interleaved image-text examples in the prompt and ask it to solve a new task without parameter updates. ICL is sensitive to example order ("lost in the middle"), example relevance, and prompt design. Order can change accuracy by 10-20 percent. Second, unified models that can both understand and generate images. Chameleon uses discrete VQ tokens for images and a single Transformer for both modalities. Show-o unifies understanding and generation in one model but finds next-token prediction less effective for image generation. Janus-Pro decouples understanding (CLIP features) from generation (VQ Tokenizer features) and almost doubles understanding performance compared to fully unified models. The motivation is that visual simulation is critical to human reasoning, and a truly omni-modal foundation model should be able to "think visually". Chain-of-Thought, which encourages the model to think step by step, has been adapted to multimodal settings (Multimodal CoT) but visual planning that reasons through images rather than text is still an open challenge.

4. Multimodal Large Language Models (MLLM)

The last topic ended with LLaVA-style models and Qwen2-VL. This topic dives deeper into the MLLM architecture, the open problems with high resolution, multimodal in-context learning, and the recent shift toward unified models that can both understand and generate.

Fundamental MLLM Architecture

An MLLM has four parts. Input modalities can be text, image, video, audio, or anything else. Modality encoders convert non-text input into features (CLIP for images, audio encoders for audio). A projector or alignment layer maps those features into the language space, which can be as simple as an MLP (LLaVA) or as complex as a Q-Former (BLIP-2). The LLM backbone processes the multimodal tokens through self-attention and produces a text response.

High Resolution Open Problems

Different models handle high resolution differently. AnyRes (LLaVA-Next) picks the closest matching grid layout. LLaVA-UHD compresses with a Q-Former. Qwen2-VL extends RoPE to image dimensions and supports variable resolution natively. The takeaway is that there is no single right answer. Higher resolution helps OCR and small object detection but hurts general task performance if not handled carefully, because more visual tokens dominate the context budget.

A revealing study on GPT-4V counting tasks ("how many circles are in this image?") showed that the model overestimates objects in the centre of the image most, less at the middle edges, and is closest to correct at the corners. This is a calibration artifact of where the visual attention falls. Model responses show a significant phase change at certain resolutions, which is why proactive search of regions of interest (Chain-of-Spot) and Zoom-Refine prompting strategies have emerged. Zoom-Refine forces the MLLM to re-evaluate its initial answer using a zoomed-in crop, then combine the cropped and original views and re-check.

Multimodal In-Context Learning (ICL)

Standard instruction tuning updates model parameters. In-context learning is parameter-free: you give the model a few interleaved input-output examples in the prompt, then a new query, and the model infers the task pattern. ICL is important because it lets users adapt the model to new tasks at inference time without any training.

ICL in multimodal settings is tricky. Three sources of sensitivity matter. First, example order. Shuffling 4 examples can swing accuracy by 10-20 percent. Similar to LLMs, MLLMs favour the first and last positions, a phenomenon called "lost in the middle". Second, example relevance. Examples that are semantically close to the target question help more than random samples. Third, prompt structure. An introductory instruction that explains the task before the examples improves performance noticeably.

Visual Chain-of-Thought

Chain-of-Thought (CoT) is a method that elicits reasoning by generating intermediate steps before the final answer. Adding "Let's think step by step" before the answer was shown by Kojima et al. to enable zero-shot reasoning in LLMs. Multimodal CoT extends this to vision-language models: the model first generates a textual rationale based on the image, then produces the final answer.

The open challenge is whether models should reason in language at all for visual problems. Some reasoning problems are inherently spatial. Visual planning, where the model reasons over intermediate visual states rather than verbalising every step, may be more natural but is hard to make faithful and constraint-aware. World models, which predict possible future visual states from history and alternative actions, are seen as a pathway toward autonomous intelligence.

Unified Multimodal Models

Up to this point, MLLMs can read pixels but not write them. They can describe an image but not generate one. Unified foundation models try to handle both directions. Chameleon (Meta) uses discrete VQ tokens. An image is quantised through a codebook (8192 entries) into a sequence of token IDs that look just like text tokens to the model, so a single Transformer handles both with mixed-modal early fusion. Show-o follows a similar idea but observes that next-token prediction is suboptimal for image generation because images are more spatially structured than text.

Janus-Pro decouples the two directions. For understanding, it uses CLIP-style features. For generation, it uses VQ Tokenizer features. The two pipelines share a Transformer backbone but use different encoders and decoders. Discrete tokenizers lose fine detail, so the decoupling lets each side use the representation best suited to its task. Janus-Pro almost doubles the multimodal understanding performance of fully unified MLLMs.

Why Unified Matters

Humans use non-verbal reasoning constantly. Visual simulation is critical for things such as predicting whether a tower will fall, planning a route, or imagining how to fold a shirt. If models are restricted to text-only reasoning, they will miss problems that are easier to solve by "thinking in pictures". A truly omni-modal foundation model is the long-term vision.

5. High-Dimensional Data Indexing

You now have embeddings that capture semantics. The next problem is engineering: how do you store billions of high-dimensional vectors and find the nearest neighbours to a query in milliseconds? This is the vector database problem, and it is the foundation of every RAG system.

Why Vector DBs Are Different

Traditional databases such as MySQL and PostgreSQL store structured data in rows and columns (user info, product IDs, timestamps) and rely on keyword matching. A query for "laptop crashed before submission" against a help-desk FAQ table fails because exact keyword overlap is rare. Vector databases instead store high-dimensional embeddings produced by neural networks and search by similarity in that embedding space. "iPhone" and "Samsung" map to nearly identical vectors because they are semantically related, so a query "Samsung" can retrieve documents about iPhones if the database thinks they are conceptually close.

The core capability is calculating distance between a query vector and millions of candidate vectors quickly. The standard metrics are cosine similarity (cos θ = A·B / (|A||B|), measures the angle) and Euclidean distance (L2, measures straight-line distance). L1 (Manhattan) and inner product are also supported.

Exact versus Approximate Nearest Neighbour

Exact k-NN search through a flat index is trivially correct: you compute the distance from the query to every vector and return the k smallest. The accuracy is perfect, but the cost is O(N) per query, which is unacceptable for billion-scale data. As dimension grows, classical structures such as KD-trees collapse into the same O(N) linear scan because every cell ends up containing most of the data (this is the curse of dimensionality at the indexing level).

Approximate Nearest Neighbour (ANN) search relaxes the requirement. You are allowed to return points whose distance is at most c times the true nearest distance. ANN trades off three things: runtime, accuracy (often measured by recall, the fraction of true neighbours retrieved), and memory consumption. This trade-off is the central engineering decision in vector databases.

Three Approaches to ANN

Partitioning (IVF)

Inverted File Index (IVF) splits the data into clusters using k-means. At query time, you find the centroid closest to the query and only search vectors in that cluster. You can also probe the top-n nearest clusters for better recall. The two tunable parameters are how many clusters to build (more clusters means smaller buckets and faster search per probe but lower recall per probe) and how many clusters to check (more probes means better recall but slower search). IVF combines well with product quantization (PQ) to compress the vectors, giving IVF-PQ, which is the workhorse for billion-scale data.

Quantization (PQ)

Product Quantization slices each high-dimensional vector into M sub-vectors and quantises each sub-vector independently to one of K codes via k-means. A vector of dimension 128 split into 8 sub-vectors of dimension 16 with K=256 becomes 8 bytes total, a 64-fold compression. Distance to a query is computed approximately by table lookup, which is fast. The trade-off is some accuracy loss because of the quantisation step.

Graph-Based (HNSW)

Hierarchical Navigable Small World (HNSW) is a proximity graph. Nodes are vectors, edges connect vectors that are close to each other. To search, you start at a predefined entry point and greedily walk along edges toward the query, jumping to whichever neighbour is closer. The hierarchical part is borrowed from skip lists: the top layer has very few nodes that are spread far apart, lower layers have more nodes that are closer together. You start at the top layer to quickly find the general region, then drop down layer by layer to refine.

Three parameters tune HNSW. The number of edges per node (M) controls memory and recall. The search width during build (efConstruction) and query (efSearch) control how aggressively the algorithm explores. Bigger numbers improve recall at the cost of latency and memory. HNSW is what powers Milvus, FAISS (when configured with HNSW index), Chroma, and many others.

Dimension mismatch: if you change embedding models, you have to re-index everything because the vector length changes (OpenAI is 1536, many HuggingFace models are 768). Lock your embedding model at the start. Metadata performance trap: searching "2023 financial reports" may fail with post-filtering (find top 100 then filter by date) because the filter eliminates results you needed. Ensure pre-filtering support so the date constraint applies before the vector search.

LlamaIndex and Data Pipelines

LlamaIndex is a data framework that handles the full lifecycle: ingest (LlamaHub connectors for PDFs, websites, Slack, multimodal documents), index (chunking, embedding, storing in a vector DB), and query (retrieving relevant chunks for an LLM prompt). Demo parameters worth knowing: similarity score (which chunk matched and how strongly), system prompt (instructions for the LLM), response length, temperature (low for faithful, high for creative), number of clusters and probes (IVF), edges per node and search width (HNSW). The full RAG pipeline is offline (extract → embed → index) plus online (query → retrieve → augment → generate).

6. Token Reduction and Information Bottleneck

Self-attention scales quadratically with sequence length. For a vision-language model, the cost is proportional to (N_text + N_image) squared. Doubling image tokens leads to roughly 4× more compute. High-resolution images quickly dominate cost. So if we want fast inference and reasonable memory, we have to reduce the number of tokens. This topic is the theory and methods for doing that.

How Many Tokens Does an Image Have?

There is no single token count per image because it depends on the model. For text, one word is roughly one or two tokens. For images, the count depends on the resolution and the patch size. The basic formula is:

$$N_{\text{tokens}} \approx \left\lceil \frac{\text{width}}{\text{patch size}} \right\rceil \times \left\lceil \frac{\text{height}}{\text{patch size}} \right\rceil$$

A 1920 by 1080 image at patch size 16 produces about 8160 patches. If the model caps at 6144 patches, you must resize the image so that the new patch count fits. For example, with effective token size of 32 by 32 and 4 patches pooled per token, resizing to 1664 by 928 gives 6032 patches and 1508 final tokens. Some architectures add special "newline" tokens at the end of each row of patches to help the model understand 2D structure when flattened to 1D.

Why Reduce Tokens

The observation that motivates everything in this topic is that there is redundancy in image tokens. Many patches are irrelevant backgrounds, many tokens are similar to others, and some tokens are noise. Studies on ViT show that you can remove most background tokens and the classifier still identifies the object as a horse. Even with aggressive removal, recognition often survives. So reducing the number of image tokens N can give a significant reduction in complexity with minimal performance loss.

Four Methods

1. Token Pruning

Z is a subset of X. Assign an importance score to each token and keep only the top-K.

Scoring methods: an MLP-based predictor (DynamicViT), [CLS] attention weights averaged across heads (EViT), or accumulated attention with Inverse Transform Sampling on the CDF (ATS).

Pros: straightforward, easy to interpret and visualise, consistent with human intuition.

Cons: irreversible information loss, often requires finetuning to recover performance.

2. Token Merging

Z consists of merged tokens from X. Merge similar tokens into a fused representative.

Algorithm (ToMe): split tokens into Group A and Group B, compute cosine similarity for every cross-group pair, take the top-K most similar pairs, merge them with weights, update attention via A = softmax(QKᵀ/√d_k + log s) where s reflects token importance.

Pros: smoother performance degradation than pruning, preserves information, usually finetuning-free.

Cons: may blur distinctions that matter for fine-grained tasks (merging "cat ear" with "dog ear" creates ambiguous "animal ear"), expensive for long sequences.

3. Token Routing

Z can include previously unselected tokens. A router decides per token whether to compute, skip, or aggregate at each layer.

Examples: IdleViT reselects tokens that were inattentive in shallow layers. MoD (Mixture-of-Depths) uses a router to decide whether each token bypasses a layer. Evo-ViT splits tokens by accumulated attention into a slow-update group and a fast-update group.

Pros: information is preserved (only compute is skipped), allows dynamic compute allocation.

Cons: increased hallucination risk, memory overhead for cached tokens.

4. Token Resampling

Z learns from X. A small set of latent queries pulls information from the input.

Examples: Perceiver uses Z = softmax(Q_q K_X^T / √d_k) V_X + Q_q. Flamingo uses a Perceiver resampler that reduces image tokens to 64. BLIP-2's Q-Former is a resampler that reduces a ViT output (257 tokens) to 32 tokens.

Pros: very high compression ratio, end-to-end trainable, preserves semantics well.

Cons: extra architectural complexity, needs finetuning or retraining.

Pruning and merging can be combined dynamically. PPT prunes inattentive tokens (likely noise) and merges duplicative ones (redundant signal). ToFu uses pruning in shallow layers where features are coarse and merging in deep layers where fine-grained patterns matter. Token routing is the most general view: pruning and merging are special cases where tokens are never re-used.

Information Bottleneck (IB) Theory

The information bottleneck principle provides a unified theoretical lens. The idea is to learn a compressed representation Z of input X that retains maximum information about target Y. The objective is:

$$\min_{p(z|x)}\; I(X; Z) - \beta \cdot I(Z; Y)$$

Here I(X; Z) is the mutual information between input and compressed representation, which we minimise to compress, and I(Z; Y) is the mutual information between compression and target, which we maximise to retain accuracy. β is a Lagrange multiplier that controls the trade-off.

From the IB view, the goal is to maximise I(Z; Y) (task info) while minimising I(Z; X) (input info). Two methods can compress equally (same number of tokens removed) but yield very different downstream performance: a good method keeps the predictive structure, a bad method keeps irrelevant detail. Compression ratio is not the same as quality of retained information.

Caveats When Choosing a Method

A few subtleties matter in practice. A token can look unimportant locally but become critical later in the computation: importance scores from attention or gradients are "who matters now" not "who matters later". In VLMs, image patch tokens may have low early attention but get fused into text representations in deeper layers and suddenly become important. Pruning early can remove latent carriers of information and break compositional reasoning.

For merging, preserving information is not the same as preserving the right information. Even if entropy is preserved, structure may be lost and distinctions blur. Merging is safer than pruning for global understanding but worse for fine-grained classification. Routing solves this by preserving information while only skipping compute, but it adds memory overhead. Resampling is best when structure is complex, importance is distributed, tokens interact globally, and you need strong generalisation.

7. Multimodal Retrieval-Augmented Generation

RAG matters because LLMs have four problems. First, static knowledge: training data is frozen at a point in time. Second, hallucinations: LLMs predict the next word from priors and produce plausible but incorrect answers. Third, cost: retraining requires millions of new examples but RAG is in-context learning. Fourth, context window: you cannot just feed everything in, context management is more important than the model itself.

The RAG Pipeline

A naive RAG pipeline has three stages, all of which can fail. First, chunking the documents into manageable pieces. Second, retrieving the top-k relevant chunks given a query (using ANN search on embedding vectors, covered last topic). Third, generating an answer by feeding the retrieved chunks plus the query into an LLM.

Where Naive RAG Goes Wrong

Three common failure modes: (1) broken chunks because the splitter cuts ideas mid-sentence, (2) irrelevant documents because the retriever has poor semantics, (3) wrong conclusion because the generator ignores or misuses the retrieved evidence.

Chunking Strategies

Chunking breaks long text into pieces for retrieval. Four strategies in order of sophistication:

  • Fixed-size chunking: straightforward but splits ideas mid-sentence.
  • Recursive chunking: more structured and hierarchical. Start with sections, drop into smaller units if too large. LangChain's default RecursiveCharacterTextSplitter.
  • Semantic chunking: focus on meaning, analyse semantic relationship and determine where to split (new topic). Computationally expensive.
  • Agentic chunking: let an LLM decide. Token-expensive but most accurate.

Practical sizing: most embedding models cap at a token limit (BERT 512, text-embedding-3 8192). Recommended chunk sizes are 250-512 tokens for general documents and 500-1000 for legal documents. Overlap is 10-20 percent generally, 25 percent for technical docs.

BM25 and Hybrid Search

Even good chunking still loses critical information sometimes. Embeddings are good at semantic match but can miss specific identifiers, error codes, or rare strings. The Anthropic Contextual Retrieval paper notes that a query for "Error code TS-999" might fail with embeddings because the model gets the general topic right but misses the specific code, while BM25 (a text-string-matching algorithm) finds the exact match.

BM25 is a bag-of-words retrieval function that ranks documents based on query terms. It combines Term Frequency (TF) and Inverse Document Frequency (IDF) but with a twist. TF in BM25 saturates: early occurrences of a term signal topic relevance but later occurrences add diminishing information. BM25 has two tunable parameters: k_1 controls term frequency saturation (1.2 to 2.0; smaller for noisy documents, larger for short documents where frequency is a strong signal) and b controls document length normalisation (0.3 to 0.9; smaller penalises long documents more).

BM25 Score
$$\text{score}(D, Q) = \sum_{i} \text{IDF}(q_i) \cdot \frac{\text{tf}(q_i, D) \cdot (k_1 + 1)}{\text{tf}(q_i, D) + k_1 \cdot \bigl(1 - b + b \cdot \tfrac{|D|}{\text{avgdl}}\bigr)}$$

Contextual Retrieval combines both. The pipeline is: chunk the corpus into pieces, create both TF-IDF encodings and semantic embeddings for each chunk, use BM25 to find top chunks based on exact matches, use embeddings to find top chunks based on semantic similarity, combine the two lists using a rank fusion technique, add the top-k results to the prompt. Anthropic also prepends an LLM-generated context to each chunk before embedding (e.g., "The company is growing fast..." appended to "The company's revenue grew by 3% over the previous quarter"), which helps retrieval because the embedding sees the global context.

Rerankers and Rank Fusion

After initial retrieval, rerankers improve hit rate and Mean Reciprocal Rank. A reranker is a more expensive model that re-scores the top candidates with a richer interaction between query and document. Cohere Rerank and BGE-Reranker are popular dedicated rerankers. RankGPT uses an LLM to do zero-shot listwise reranking with a sliding window strategy when candidate count exceeds LLM context.

If you do not want to train a separate reranker, Reciprocal Rank Fusion (RRF) combines ranked lists from multiple retrievers using rank positions instead of raw scores. The formula is:

$$\text{RRF}(d) = \sum_{i} \frac{1}{k + \text{rank}_i(d)}, \qquad k \approx 60$$

It is cheap, easy, and surprisingly effective.

The MRAG Roadmap

Multimodal RAG has gone through three generations.

  • MRAG 1.0 (pseudo-MRAG): convert images, tables, and other media to captions or OCR text, then run text-only RAG. Easy to build but modality conversion causes information loss and creates a retrieval bottleneck.
  • MRAG 2.0 (true multimodal): preserve original multimodal data, support multimodal retrieval, use an MLLM to generate from multimodal evidence directly.
  • MRAG 3.0: end-to-end multimodality with document screenshots, multimodal search planning, and multimodal outputs instead of text-only answers.

ColPali and Late Interaction

ColPali is a representative MRAG 2.0 system. Performance bottlenecks in practical RAG are usually in the data ingestion pipeline (parsing dirty PDFs with tables, charts, layout) rather than in embeddings or chunking. ColPali sidesteps the parsing problem by embedding entire document page screenshots directly. The encoder is PaliGemma (a VLM) finetuned to produce embeddings, with the language modelling head removed. Training uses a contrastive loss similar to CLIP between query text and page images.

Late interaction is the middle step between single-vector embedding and full reranking. Instead of one vector per document, ColPali produces a multi-vector representation (one vector per visual token in the page). At query time, each query token is matched against all document tokens and the maximum similarity per query token is summed. This catches fine-grained matches that single-vector embeddings miss while remaining cheaper than full pairwise reranking.

Jina-Embeddings-v4

Jina-Embeddings-v4 is a universal embedding model for multimodal multilingual retrieval. The 3B parameter model supports both single-vector (truncated to 128-dim) and multi-vector outputs (N tokens of 2048-dim). It uses Multimodal RoPE and is trained with PEFT (covered later). A key finding is the cone effect: contrastive training creates a bias where each modality forms its own cluster in embedding space, and even after training pulls matched pairs together, the embeddings form a high-dimensional cone-like bridge rather than truly mixing. The modality gap shows up clearly when you compare image-text similarity to text-text similarity. Jina's multi-vector approach reduces this gap compared to OpenAI CLIP.

What Works in Practice (ViDoRe V3)

ViDoRe V3 evaluates MRAG in real-world scenarios. Findings: visual retrievers outperform textual ones even with text queries. Text rerankers outperform visual ones. Hybrid retrieval performs best by F1 (concatenate top-5 from visual and textual retrievers without removing duplicates). Image-based context outperforms text-based context because images provide more visual cues for grounding. Charts, layouts, and figures are the hardest question types because they require both spatial reasoning and language.

Agentic RAG

Agentic RAG decides which tool to use and whether re-retrieval is needed. Examples include Search-o1 and VISOR, which iteratively search, reason over horizons, and refine. DeepResearch-style systems perform multi-step search planning where each retrieval informs the next query.

LLM Wiki: When You Do Not Need RAG

Karpathy proposed an alternative called LLM Wiki: stable, frequently used knowledge can be compiled into the model itself through training or memory rather than retrieved every time. The idea is three operations: ingest into a wiki structure, compile into the model, and amortise the retrieval cost over many queries. Long-frequency information that may change over time stays in RAG. Stable evergreen facts go in LLM Wiki. Future systems will be hybrid: retrieve fresh raw evidence, compile stable reusable knowledge.

Prompt Design for MRAG

Tutorial 7 covers prompt design for MRAG carefully. Multimodal RAG can fail even after correct retrieval if the prompt does not tell the model how to use the retrieved evidence. The structure should split into a System Prompt (defining the assistant's role, requiring evidence-based answering, preventing unsupported details, handling insufficient evidence) and a User Prompt (the question, the retrieved text, the retrieved image, the expected format).

Prompt strength increases in stages: from "answer the question" to "answer using the retrieved evidence" to "answer using only the retrieved evidence" to "if the evidence is insufficient, say so clearly". When there is too much retrieved context, three strategies help: truncation (keep top-ranked), query-aware compression (keep parts most relevant to the question), segment and summarise. The model should rely more on the image when the question is about visible objects, colour, shape, count, or spatial relationship; more on text for background facts, metadata, and non-visible context.

8. Multimodal RAG Evaluation and Hallucinations

Retrieval is necessary but not sufficient. Correct evidence can still lead to incorrect answers because the generator may ignore evidence, over-trust priors, or fuse modalities badly. MRAG needs layered evaluation: retrieval quality, answer quality, and groundedness.

Retrieval Metrics

The first evaluation layer is whether the retriever returns relevant documents. Non-rank-based metrics treat retrieval as a binary outcome.

Precision and Recall

Precision is the fraction of retrieved documents that are relevant. Recall is the fraction of relevant documents that are retrieved. A retrieval model can cheat recall simply by increasing k, which is why people also report F1, the harmonic mean of precision and recall.

Rank-based metrics evaluate the order in which relevant items appear.

Mean Reciprocal Rank (MRR)
$$\text{MRR} = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{rank}_i}$$

Average of the reciprocal ranks of the first correct answer across queries. Answers the question "how early is the first relevant result?"

Normalised Discounted Cumulative Gain (nDCG@K)
$$\text{DCG}@K = \sum_{i=1}^{K} \frac{2^{\text{rel}_i} - 1}{\log_2(i + 1)}$$
$$\text{nDCG}@K = \frac{\text{DCG}@K}{\text{IDCG}@K}$$

Designed for non-binary notions of relevance (graded relevance). Cumulative Gain is the sum of relevance scores. DCG adds a logarithmic discount so that relevant items further down the list contribute less. IDCG is the DCG of the ideal ranking. nDCG normalises by IDCG so the metric ranges from 0 to 1. Answers "are the most relevant results ranked highest?"

When ground-truth documents are not available, you fall back to context relevance: does the retrieved document help answer the input query? Two ways to measure: human annotation (taxing but aligns with human judgment) or LLM-as-a-judge (direct prompting or prompting plus in-context learning).

The RAG Triad (TruLens)

Beyond retrieval, two more layers exist:

  • Answer Accuracy / Correctness: does the final answer match the expected ground truth and properly respond to the user's question?
  • Faithfulness / Groundedness: are the claims in the answer supported by the retrieved context, rather than hallucinated?

Measuring Faithfulness

Faithfulness asks whether each claim in the answer can be supported by retrieved context. The standard approach uses LLM-as-a-judge: decompose the answer into atomic claims, then for each claim check whether the retrieved context supports it. RAGAs implements this pipeline with reverse engineering and decomposition. FactScore generalises it. DeepEval and TruLens are alternative frameworks with similar primitives.

MRAG-Specific Challenges

Text-centric evaluation fails in multimodal settings. Consider a radiology RAG system. Text context relevance might pass (the retrieved diagnosis is coherent with the query). Image context similarity might be high (the retrieved image looks like the query image to a CLIP-based scorer). But the actual context could be wrong: the high similarity comes from a similar-looking but clinically different case. Text-centric evaluation cannot catch this. To address it, you need query grounding: a VLM that grounds claims in the actual visual content.

Hallucinations Taxonomy

Hallucinations in MLLM are textual answers that describe visual input incorrectly. The taxonomy by Jing et al. classifies four types:

  • Object existence: the answer mentions an entity not present in the image.
  • Attribute: the entity exists but colour, count, value, state, or label is wrong.
  • Relation: entities exist but spatial, causal, or logical relation is wrong.
  • Event / temporal: video or audio sequence, action order, or time segment is misread.

FaithScore quantifies hallucinations using this taxonomy. In MRAG specifically, hallucinations break down further:

  • Query-grounding hallucination: misreads the user-provided image, chart, video before retrieval.
  • Retrieval hallucination: answer fills in facts because required evidence was not retrieved.
  • Grounding hallucination: evidence is retrieved but visually misperceived.
  • Reasoning hallucination: combines facts from multiple sources into a false conclusion.
  • Citation hallucination: claim may be true but cited source does not support it.

MiRAGE assesses hallucination in the multimodal reasoning chains of MLLMs at the level of intermediate steps, not just final answers.

Why Hallucinations Exist

Two main reasons. Statistical bias: LVLM/MLLMs memorise training data, and the distribution of objects in training affects model behaviour. The model learns spurious associations such as "scenes that look like beaches usually contain umbrellas" and predicts an umbrella even when none is present. Visual uncertainty: when visual evidence is weak (low resolution, noise, ambiguity), the model over-relies on language priors.

Mitigating Hallucinations

Visual Contrastive Decoding (VCD)

VCD is a training-free method. The model generates output distributions from both the original image and a distorted version (Gaussian noise applied). The final output is the contrast between the two distributions. The intuition: the difference is what the actual image contributes beyond mere language priors. Subtracting the noisy distribution removes the prior bias and reduces over-reliance on statistical and unimodal priors. Think of it as self-correcting decoding.

$$p_{\text{VCD}}(y \mid x_{\text{image}}, \text{prompt}) = \text{softmax}\!\bigl((1+\alpha)\,\ell(x_{\text{image}}, p) - \alpha\,\ell(x_{\text{noisy}}, p)\bigr)$$

RL-Based Mitigation

You can train the model to prefer not to hallucinate. Hallucination-Aware DPO collects pairs of (grounded, hallucinated) answers and uses Direct Preference Optimization to push the model toward the grounded ones. This works because DPO aligns modalities and reduces hallucination as a side effect. We cover DPO in detail in the next topic.

Is MRAG Evaluation Sufficient?

The hardest failure may not be saying something false, it is missing the obvious truth. Consider an agent looking at a campsite photo and being asked "what is missing for the camper?" The agent can observe most details correctly, cite or describe evidence faithfully, but if it fails to notice that no tent is set up, it has failed the task. This is the gap between claim-level correctness and problem-level understanding. Did the system identify the evidence that actually matters?

9. Agents

So far we have models that reason, reflect, and remember. But that is not yet an agent. An agent is a task-solving system that can plan, use tools, access external data, and act across digital environments. In reinforcement learning, an agent is an intelligent system that learns actions through interaction with an environment, physical (robots, autonomous cars) or digital (DQN for Atari, AlphaGo, Siri). In the era of LLMs, a language agent is an LLM that dynamically directs its own processes and tool usage, maintaining control over how it accomplishes tasks.

Language Agent Pipeline

The agent loop has four components. The LLM/MLLM core handles reasoning and language generation. Memory comes in two flavours: short-term (prompting and in-context learning) and long-term (vector store, the RAG pipelines from the previous topics). Planning and reasoning use frameworks such as ReAct, CoT, and Reflexion. The environment can be a desktop OS, web browser, mobile apps, games, robots, or databases. The agent reasons, observes the environment, and acts by calling tools, interacting with the user, or producing a response.

Key Concepts

  • Action space: internal actions (reason, plan, reflect), information actions (retrieve, search, query DB), tool actions (call APIs, run code, generate charts).
  • Reasoning: for humans various mental processes, for LLMs intermediate generation, for agents asking "why action needed, why now?"
  • Planning: at inference time, decide which action to take next.

ReAct Framework

ReAct stands for Reasoning plus Acting. It is a prompting framework that interleaves language-based reasoning with external actions. The loop is Thought → Action → Observation → Thought → Action → ... The model writes a thought (internal reasoning), takes an action (external tool call), receives an observation (the result), and continues. Reasoning guides acting and acting also guides reasoning, because new observations let the model revise its plan and correct earlier assumptions. This reduces unsupported guessing and hallucinations compared to a single-shot LLM answer for multi-step tasks.

The flexibility of acting matters. JSON function calling has a limited set of predefined tools and is restrictive. A unified action space using Python code lets the agent write arbitrary code at runtime, which is far more expressive. The flexibility of reasoning also matters: reasoning is operational in some contexts (track research status, check facts) and narrative or social in others (reflect intention, infer impressions). Unlike traditional game actions like jump or move left, agent actions include a thought, a plan, a reflection, a fact check, or a tool-selection rationale.

Reasoning Control

Two ways to control which reasoning path the agent follows:

  • Inference-time control: sample, vote, search, backtrace.
  • Train-time RL optimization: imitate, prefer, reward, reinforce.

Self-Consistency

CoT usually follows one greedy decoding path. Self-consistency samples multiple greedy decoding paths, extracts the final answer from each, and majority votes. This works because correct answers tend to be reached via multiple reasoning paths while incorrect ones diverge.

Tree of Thoughts (ToT)

ToT treats each intermediate thought as a search state. It samples or proposes multiple candidate thoughts at each step (when a thought is a paragraph or word), evaluates which thoughts are promising, and performs BFS or DFS over reasoning paths. BFS maintains a set of b (b ≤ 5) most promising states per step. DFS explores the most promising state first until the final output is reached, otherwise prunes subtrees. The famous worked example is Game of 24 (use four numbers with arithmetic to make 24).

RL Post-Training

Prompting controls reasoning at inference time but does not reliably change the model's underlying policy. Prompting may produce verbose but wrong reasoning, and for agents wrong reasoning affects tool choices and future observations. Post-training the model with RL internalises strategies that prompting alone could not.

RLHF

Reinforcement Learning from Human Feedback uses human judgment as the reward signal. Many real-world goals are hard to write as a reward function, and bad rewards lead to reward hacking, so RLHF asks humans to pick the best of multiple candidate answers (pairwise comparison or eval style) and trains a reward predictor from those preferences. The mathematical model for pairwise comparison is the Bradley-Terry logistic preference loss. The full pipeline is SFT → Reward → Policy. After fitting the reward model, you use it to train the RL policy via PPO.

Proximal Policy Optimization (PPO)

PPO penalises policies from changing too much between steps (since we already have a language policy from SFT). The idea is to clip the objective function whenever the policy differs too much from the old policy. The PPO objective involves a likelihood ratio that measures how likely the new policy is to choose the same action and an advantage function that measures whether the action contributed to a better-than-expected output. A KL divergence term prevents the policy from moving too far from the reference model.

PPO Objective (simplified)
$$\mathcal{L}_{\text{PPO}} = \mathbb{E}\!\left[\min\!\bigl(r(\theta)\,A,\ \text{clip}(r(\theta), 1-\varepsilon, 1+\varepsilon)\,A\bigr)\right] - \beta \cdot \text{KL}(\pi_\theta \,\|\, \pi_{\text{ref}})$$

r(θ) is the ratio of new to old policy probabilities, A is the advantage. KL divergence prevents drift from the reference model.

Direct Preference Optimization (DPO)

DPO is simpler than RLHF. Instead of training a separate reward model and then doing RL, DPO directly optimises the policy using preference pairs. The key insight is that when you substitute the reward into the RL objective, the log Z(x) term cancels because the loss only cares about differences in rewards. So you can optimise the policy directly on (preferred, dispreferred) pairs without ever fitting a reward model. The implicit reward modelling tends to do better than explicit modelling.

DPO Loss
$$\mathcal{L}_{\text{DPO}} = -\log \sigma\!\left(\beta \left[\log \frac{\pi_\theta(y_w | x)}{\pi_{\text{ref}}(y_w | x)} - \log \frac{\pi_\theta(y_l | x)}{\pi_{\text{ref}}(y_l | x)}\right]\right)$$

y_w is the preferred (winner), y_l is the dispreferred (loser). β controls how strongly the model deviates from the reference.

DPO is attractive for reasoning alignment because reasoning quality is often easier to compare than to score. Preference pairs can compare correct versus incorrect reasoning, grounded versus hallucinated reasoning, safe versus unsafe tool use. DPO also helps reduce multimodal hallucination (this is what gets used in the previous topic). The limits: depends on preference data quality, offline pairs do not encourage exploration, and hard for long-horizon agent tasks (web, code, robotics, multi-step tool use).

Group Relative Policy Optimization (GRPO)

GRPO is the DeepSeek innovation. From PPO to GRPO: reasoning tasks often allow multiple attempts for the same prompt (as in self-consistency and ToT), so we can compare them to each other instead of needing an external value model. GRPO generates multiple responses for one question and computes the advantage of each response relative to the group:

$$A_i = \frac{r_i - \operatorname{mean}(r_1, \ldots, r_G)}{\operatorname{std}(r_1, \ldots, r_G)}$$

The objective is similar to PPO but uses group-relative advantage and removes the value model. The model is updated to maximise the objective, with a KL term to keep it close to the reference. Rewards in GRPO are rule-based: accuracy rewards (correct math, correct LeetCode), format rewards (the model puts thinking between <think> tags). DeepSeek-R1-Zero used pure RL with GRPO to surpass OpenAI-o1 on reasoning benchmarks.

PPO vs GRPO in One Line

PPO needs a separate value model that estimates expected future reward at every state, which is expensive. GRPO removes the value model and estimates advantage by sampling a group of responses for the same prompt and comparing them. This works because reasoning tasks naturally allow multiple attempts.

From Tools to Tool Ecosystems: MCP

Function calling connects one model to one tool. Every integration has different API schema, authentication, permission model, and response format. Adding a new tool means writing another integration.

MCP (Model Context Protocol) standardises how tools and data plug into agents. The architecture has three components: a Host (the AI application), a Client (the connection manager inside the host), and Servers (which expose tools, resources, and prompts). MCP makes tool capabilities reusable across agent clients. It supports connections to files, databases, IDEs, calendars, maps, and productivity tools.

MCP helps with exposing tools, discovering capabilities, passing structured arguments, returning structured results, and reusing tools across hosts. MCP does not decide which tool to use next, whether the result is enough, whether to retry, how to branch, how to store state, how to recover from failure, or how to synthesise the final answer. Those are the responsibilities of the agent framework above MCP.

LangGraph: Workflow Control

LangGraph represents an agent workflow as a graph with four primitives: State (current task information), Nodes (perform work and update state), Edges (determine which node runs next), Conditional Edges (dynamic routing based on state). Common patterns include sequential prompt chains (output of one call becomes input to the next), parallel processing (run multiple LLM calls in parallel and combine), orchestrator-worker (an orchestrator breaks tasks into subtasks, delegates to workers, synthesises results), evaluator-optimizer (one agent generates, another evaluates against success criteria, route back if needed). The Send primitive dynamically dispatches subtasks. Conditional edges enable loops such as "if missing info, search again".

Real Agents = Real Risk

An example personal agent system is OpenClaw, which runs locally and integrates with real-world tools (WhatsApp, Telegram, Slack). Real agents have privileged access to files, emails, and APIs. The risks include prompt injection (an attacker feeds malicious instructions through user-visible content), malicious skills (third-party tools that misbehave), and data leakage. Multimodal agents (such as AgentThink for autonomous driving) extend reasoning with vision tools, but the same risks apply.

10. Parameter-Efficient Fine-Tuning (PEFT)

Supervised Fine-Tuning (SFT) adapts a pretrained LLM by optimising it on curated instruction-response examples, usually with next-token prediction on the assistant response. Full SFT updates the entire model. The pretrained backbone (attention, MLP, all trainable layers) is updated: W' = W_0 + ΔW where ΔW is what training learned. This becomes increasingly expensive as LLMs scale.

Full fine-tuning at this scale is not realistic for most use cases.

What PEFT Is

PEFT is a family of methods that adapt a pretrained model by freezing most of the backbone and training only a small number of additional or selected parameters. The goal is to retain most of the performance of full SFT while reducing training, storage, and deployment cost.

Three main families based on where trainable parameters are added:

Prompt-Based PEFT

A text prompt is a human-written instruction tokenised into discrete tokens. A learnable prompt (soft prompt) is a small set of trainable virtual token embeddings optimised by gradient descent. Text prompts are readable but not trainable, soft prompts are trainable but not readable.

Prompt Tuning is the simplest variant. Freeze the pretrained LLM, prepend a short sequence of trainable virtual token embeddings to the input embeddings, train only those embeddings on downstream data, and all LLM weights stay frozen. Prompt Tuning becomes stronger as model size increases. At very large scale, on some tasks and model families, it can approach full model tuning while training far fewer parameters.

P-tuning and P-tuning V2 extend the idea. P-tuning learns continuous prompts, optionally generated by a prompt encoder. P-tuning V2 (deep prompt tuning) adds trainable prompts to multiple Transformer layers, not just the input. The key change is from input-only soft prompts to layer-wise prompt parameters. P-tuning V2 closes much of the gap between prompt tuning and full fine-tuning.

Adapter-Based PEFT

Adapters insert small trainable modules into a frozen Transformer. The backbone stays frozen, only adapter modules are trained.

The Houlsby Adapter follows a bottleneck pattern: down-project, non-linearity, up-project, residual add:

$$h' = h + W_{\text{up}}\,\sigma(W_{\text{down}}\,h)$$

It gives strong performance while updating far fewer parameters than fine-tuning the upper layers of the model.

AdapterFusion solves the problem that a single task adapter is modular but isolated. If you train many adapters across tasks, useful knowledge does not automatically combine. AdapterFusion has two stages. Stage 1 (knowledge extraction) trains one adapter per source task with the backbone frozen. Stage 2 (knowledge composition) freezes the backbone and all source adapters, then trains an attention-based fusion layer that dynamically combines adapter outputs. At inference the fusion layer selects useful information from multiple adapters. The fusion activation heatmap shows which target tasks rely on which source adapters: bright entries indicate the fusion layer pulls strongly from that source.

LoRA (Low-Rank Adaptation)

LoRA is the practical default in modern PEFT. The idea is that the update ΔW learned during fine-tuning often has low intrinsic rank: it can be approximated by a product of two thin matrices. LoRA freezes W_0 and learns ΔW = B·A, where only A and B are trainable. A has shape (r, d) and B has shape (d, r), with r much smaller than d. Together they reconstruct a full d×d update.

Example: for an 8.56B parameter model, LoRA can use only 22.1M trainable parameters. The rest stay frozen. The original LoRA paper applied LoRA mainly to attention projection matrices (q_proj, k_proj, v_proj, o_proj). Modern fine-tuning often extends LoRA to more linear layers (including MLP layers) for stronger adaptation.

LoRA at Inference

During training the output is h = Wx + BAx (the original path plus the LoRA branch). Before inference you can merge the learned update into the base weights: W' = W + ΔW where ΔW = BA. After merging you use a single adapted weight matrix W' with no separate LoRA branch, so inference latency is identical to the base model.

This supports the claim that useful updates concentrate in a low-dimensional subspace.

QLoRA

QLoRA combines 4-bit quantisation with LoRA. The frozen backbone is quantised to 4 bits (0.5 bytes per parameter) instead of 16 bits (2 bytes). The LoRA adapters stay at higher precision. The memory saving is dramatic: a 65B model in 16-bit takes about 130 GB, in 4-bit it takes about 32.5 GB. Lower precision introduces approximation error but largely preserves 16-bit fine-tuning performance.

DoRA (Weight-Decomposed Low-Rank Adaptation)

DoRA is LoRA with weight decomposition. Instead of adapting W directly, DoRA separates two quantities: magnitude (how large the weight vector is) and direction (where the weight vector points). DoRA uses LoRA to update the direction and learns the magnitude m separately. The adapted weight is learned magnitude times normalised updated direction.

Full fine-tuning changes both magnitude and direction. LoRA changes the weight matrix through one low-rank ΔW, so magnitude and direction changes are entangled. DoRA explicitly separates them, making its update behaviour closer to full fine-tuning. Empirically DoRA outperforms LoRA, especially at low ranks (r = 4 or r = 8 give the biggest gains), which makes DoRA attractive when you want to push parameter efficiency further.

Recent LoRA-Family Directions (2025+)

Three research directions extend LoRA. More expressive updates such as HiRA and RaSA reduce the expressiveness bottleneck of simple low-rank updates, using higher-rank structures or rank sharing. Safety-preserving adaptation such as SaLoRA fine-tunes for downstream tasks while reducing damage to the base model's safety alignment. Multi-adapter composition such as MeteoRA combines or routes among multiple LoRA adapters so different tasks reuse the same base model. These are research directions, not yet as standardised as LoRA or QLoRA.

Why LoRA Became the Default

Three reasons. First, LoRA directly approximates full fine-tuning in weight space. Prompt tuning changes input conditioning, adapters add extra transformations, but LoRA directly parameterises an additive update to existing weight matrices. Second, low-rank updates are often enough because the most useful directions in fine-tuning concentrate in a small subspace. Third, engineering advantages: small checkpoints (save only A and B), mergeable for inference (no extra latency), multi-adapter serving (one shared base model serves many task-specific LoRA adapters), quantisation-friendly (QLoRA), and supported by mainstream tooling (Hugging Face PEFT, bitsandbytes, vLLM).

Foundations and the Transformer

BEGINNERWhat is the manifold hypothesis, and why does it matter for high-dimensional data?

The manifold hypothesis is the observation that real-world data does not fill the entire high-dimensional space it lives in. Instead, the data sits on a much lower-dimensional surface called a manifold. For example, a 220 by 160 pixel colour image has about 105,600 raw dimensions, but the set of images that look like a cat occupies only a thin sliver of that space.

This matters because raw Euclidean distance in the full space is almost meaningless. As dimensions grow, the volume grows exponentially, and points become roughly equidistant from each other. The course phrases this as a "blessing of dimensionality" in disguise: we do not need to model the entire empty space, we just need to learn a function f(x) that maps raw input onto the manifold. Once on the manifold, distances become meaningful and we can do similarity search, classification, and retrieval.

Every deep learning model in this course is essentially a different way of learning that mapping function. CLIP learns a manifold shared between images and text. ViT learns an image manifold. Vector databases work because embeddings live on a manifold where distances are informative.

BEGINNERWhy does Bag of Words fail to distinguish "Dog bites man" from "Man bites dog"?

Bag of Words counts how often each word appears in a sentence without regard to order. Both sentences contain exactly the same words (dog, bites, man), so they produce identical vectors. BoW collapses meaning by ignoring syntax and position.

This is the same failure mode as a colour histogram for images: it summarises by global statistics and throws away spatial or sequential structure. The vectors are also extremely sparse and high-dimensional because you need one dimension per vocabulary word, and most documents touch only a tiny fraction of the vocabulary.

The fix in the text world was to introduce n-grams, which capture short-range word order (so "not good" gets a different feature from "good"). But n-grams blow up exponentially in size, since the feature dimension grows as V to the n, and they only catch a window of n words. The Transformer eventually solved this by using self-attention to capture arbitrary-range dependencies in a single pass.

BEGINNERWhat is tokenization and why is subword (BPE) tokenization the standard?

Tokenization breaks raw input text into a sequence of discrete units that the model can look up in an embedding table. There are three granularities to choose from. Word-level tokenization assigns one token per word, but you need a huge vocabulary and you cannot handle unseen words. Character-level tokenization solves the vocabulary problem but makes sequences extremely long, which is bad because attention cost grows quadratically with sequence length.

The compromise is subword tokenization, and the standard algorithm is Byte-Pair Encoding (BPE). BPE starts with a base vocabulary of individual characters or bytes, then iteratively finds the most frequent adjacent pair of tokens in the training corpus and merges them into a new token. After enough merges, the vocabulary contains common whole words like "the", common prefixes and suffixes like "un-" and "-ing", and individual characters for rare or unseen words.

The word "unbelievable" might tokenize as four pieces [un, bel, iev, able] in a 32K vocabulary but only three pieces [un, bel, ievable] in a 128K vocabulary. So a larger vocab compresses text into fewer tokens per word at the cost of more parameters in the embedding and output projection matrices.

To handle multilingual text and weird symbols, modern systems use byte-level BPE. Every character first becomes a sequence of UTF-8 bytes, so the base vocabulary is exactly 256 entries and any string is representable.

INTERMEDIATECompare Llama 2 (32K vocab) and Llama 3 (128K vocab) across tokenization efficiency, attention cost, parameter count, and final-layer speed.

This is the classic tutorial 1 question. Four trade-offs all stem from increasing vocabulary size.

Tokenization efficiency: Llama 3 produces a shorter sequence. A larger vocabulary allows longer subword units, so the same essay needs fewer tokens. "Unbelievable" might be four tokens in Llama 2 but three in Llama 3.

Attention cost: Llama 2 has higher attention cost for the same text. Self-attention complexity is O(n²) in sequence length. If Llama 3 cuts the sequence length by about 15 percent, attention compute drops by about 28 percent because 0.85² ≈ 0.72.

Parameter cost: Llama 3 has more parameters. Vocabulary size directly determines the size of two matrices: the input embedding matrix (V × d_model) and the output projection LM head (d_model × V). With d_model = 4K, the vocabulary increase of 96K adds 96K × 4K = 384M to each, so about 768M extra parameters total. This is roughly why Llama 3 is marketed as 8B versus Llama 2 at 7B despite similar architectural depth.

Final-layer speed: Llama 2 generates a single token faster at the output. The final hidden state must be projected to vocabulary logits using the output matrix, which grows with V. The softmax must also normalise over all V classes. Larger V increases both compute and memory bandwidth for the final layer.

The net effect is that Llama 3 is faster overall on long sequences because the attention savings dominate the slower output, but the output layer alone is slower per token.

INTERMEDIATEWhat is positional encoding, what is the extrapolation problem, and why do sinusoids and RoPE solve it?

Self-attention is permutation invariant. If you scramble the order of tokens, the set of token embeddings stays the same and attention gives the same output. That is unacceptable for sequence tasks because "dog bites man" and "man bites dog" need different representations. Positional encoding adds position-specific information to each token embedding so the model can distinguish them.

The simplest approach is Absolute Positional Embedding (APE): learn a vector for each position up to some maximum sequence length, and add it to the token embedding. APE has the extrapolation problem. If you train with sequences up to length 2048, positions 2049 and beyond have no learned vector. The model cannot meaningfully handle longer sequences than seen during training.

Sinusoidal positional encoding solves this by using fixed mathematical functions instead of learned vectors. PE(pos, 2i) = sin(pos / 10000^(2i/d)) and PE(pos, 2i+1) = cos(pos / 10000^(2i/d)). Even dimensions use sine, odd use cosine, each pair of dimensions uses a different frequency. Lower indices oscillate slowly, higher indices oscillate quickly. This generalises smoothly to any position you have not trained on because the formula is defined for any input.

The clever mathematical property is that a shift of k positions can be expressed as a linear (rotation) transformation of the original encoding. So relative position differences emerge automatically through the attention dot product.

Rotary Position Embedding (RoPE) takes this idea further by literally rotating pairs of dimensions in the Q and K vectors based on their position. Instead of adding a position vector, RoPE multiplies the query and key by a rotation matrix that depends on position. This means relative position appears naturally in the attention score QK^T, and RoPE extrapolates better than APE because rotation angles can be applied at any new position. RoPE has become the default in Llama, Qwen, and other modern models. Qwen2-VL extends RoPE to multimodal dimensions (time, height, width) with M-RoPE.

INTERMEDIATEWalk me through scaled dot-product attention from queries, keys, and values to the output, including why we divide by √d_k.

Self-attention is the workhorse of the Transformer. Each input token x_i is projected into three vectors using three learned matrices: a query Q = x · W_Q, a key K = x · W_K, and a value V = x · W_V. The intuition is that the query asks a question (what is this token looking for?), the keys advertise what each token has to offer, and the values are the content to be aggregated.

Step 1: compute attention scores. For each pair of tokens (i, j), take the dot product of query i with key j. The dot product produces a scalar that measures how relevant token j is to token i. The output is a matrix QK^T of shape (n, n).

Step 2: scale by √d_k. Without scaling, the dot product of two random d_k-dimensional vectors grows in magnitude with d_k, which would push the subsequent softmax into a regime where one position gets nearly all the probability and gradients vanish for the others. Dividing by √d_k normalises the variance back to 1 and keeps gradients stable for training.

Step 3: apply softmax row-wise to convert raw scores into a probability distribution over all positions for each query. Each row sums to 1.

Step 4: multiply the resulting attention probability matrix by V. This is a weighted sum of value vectors for each query, where the weights are the attention probabilities. The model "routes" content from the most relevant context (V) into the current position. The final formula is Attention(Q, K, V) = softmax(QK^T / √d_k) V.

Multi-head attention runs this in parallel several times with different projections, then concatenates the outputs. Each head can learn a different pattern such as syntactic dependency, semantic similarity, or positional structure. But models are heavily overparameterised, so pruning studies reveal "dead heads" that learn duplicate or useless patterns.

ADVANCEDExplain the KV cache, why it is essential for autoregressive decoding, and derive its memory footprint.

Autoregressive decoding generates one token at a time. Naively, to generate token t you treat the model as y = f(x_{1:t-1}) and feed the entire prefix through all Transformer layers to compute keys, values, and the query at every step. But the keys and values for previous tokens do not change once computed: K_i = x_i · W_K and V_i = x_i · W_V are fixed once x_i is known. So most of that computation is redundant.

The KV cache fixes this. To generate token t after having generated x_{t-1}, the steps are: compute Q_{t-1}, K_{t-1}, V_{t-1} for the new token only, retrieve the previously cached K and V from earlier steps, concatenate to form the full K_{<t} and V_{<t}, compute attention as Softmax(Q_{t-1} K_{<t}^T / √d_k) V_{<t}, then store the new K_{t-1} and V_{t-1} in the cache for the next step. This is a classic trade-off of space for time.

The memory cost can be derived. In standard multi-head attention, K (and V) per token has total dimensionality d_model across all heads. We store both K and V, so per token per layer the cost is 2 × d_model. The full cache size in bytes is:

$$\text{KV}_{\text{size}} = \text{batch} \times 2 \times L_{\text{seq}} \times N_{\text{layers}} \times d_{\text{model}} \times \text{bytes}$$

For a typical 128K-context model with N = 32 layers, d_model = 4K, FP16 (2 bytes), and batch size 1:

$$\text{Size} = 1 \times 2 \times 128\text{K} \times 32 \times 4\text{K} \times 2 = 65{,}536\,\text{MiB} = 64\,\text{GiB}$$

That is just the KV cache, before model weights, gradients, or activations.

This explains why LLMs impose hard context window limits. Memory grows linearly with sequence length. Without a limit, the cache would eventually exhaust GPU memory. Inference latency also grows because each new query must attend to all previous keys, which is O(L) per token even with caching. When you exceed the limit, systems silently drop the oldest tokens (you suddenly "forget" your instructions) or fail with a "conversation too long" message.

Context window sizes have grown over time: 4K (GPT-3.5, Llama 2 base), 32K (GPT-4-32k), 128K (GPT-4o, Llama 3.1, Qwen2, DeepSeek-R1), 200K+ (Claude 3/4 Sonnet, Yi-34B 200K), 1M (Gemini Pro/3, Claude 4 beta, GPT-4.1), and 10M+ (Llama 4 Scout, Magic). Each tier requires better attention algorithms, memory management, and distributed computing.

ADVANCEDWhy does the FFN expand to 4d, and what is the parameter breakdown of a Transformer block?

A Transformer block has two sublayers: multi-head attention and a position-wise feed-forward network (FFN). Each sublayer is wrapped in a residual connection with LayerNorm.

The FFN is a two-layer MLP with a non-linearity (ReLU or GELU). It first expands from d to 4d, applies the non-linearity, then projects back from 4d to d. Why 4d? Expanding to a higher intermediate dimension creates a richer non-linear basis. The model can express more complex transformations in the wider space before squeezing back down. Empirically 4d is the sweet spot: lower hurts capacity, higher gives diminishing returns at significant compute cost.

The parameter count of a single Transformer block is:

  • Attention projections: W_Q + W_K + W_V + W_O = d² + d² + d² + d² = 4d²
  • FFN: W_1 + W_2 = d · 4d + 4d · d = 4d² + 4d² = 8d²

So the FFN alone is twice as expensive as all four attention projections combined. Most of the compute and parameters in a Transformer live in the FFN, not in attention. This is part of why people are excited about alternatives like Mixture of Experts (MoE), which sparsifies the FFN.

One more design choice. Should you "Add first then Norm" or "Norm first then Add"? Post-norm (Add then Norm) was the original Transformer. Pre-norm (Norm then Add) is more stable at depth because gradients flow through the residual path without going through LayerNorm. Modern Transformers default to pre-norm for this reason.

Self-Supervised Embedding

BEGINNERWhat is self-supervised learning, and how does it differ from supervised learning?

Supervised learning is Y = f(X), where you have input X (an image, a text) and an externally provided target Y (a class label from a human annotator). The model learns the mapping from data points to labels by minimising prediction error against the provided labels.

Self-supervised learning (SSL) is a special form of representation learning where the labels come from the data itself, not from an external annotator. There are two main families:

  • Self-prediction (X_i from X_i): given one sample, hide part of it and predict the missing part from the remaining part. Examples: masked language modelling (BERT), masked image autoencoding (MAE), predicting image rotation, predicting patch position.
  • Contrastive (X_j from X_i): given multiple samples, predict their relationship. Samples can be selected from the dataset based on known logics (such as word order) or fabricated by augmentation. The most common pretext task is matching two augmented views of the same image.

Yann LeCun once compared this to a cake: SSL is the cake (most of the signal), supervised learning is the icing, and reinforcement learning is the cherry on top. This means SSL is the dominant source of learning signal when training at scale.

SSL matters because labels are expensive and scarce, especially in vision where each image gets only one classification label. SSL creates dense, automatically generated learning signals that scale with data size. This is exactly what made GPT and ViT possible at the scales we see today.

BEGINNERWhat does the scaling law say about LLM performance, and what does it tell you about diminishing returns?

The scaling law is the empirical observation that model performance (measured by loss or error) follows a power law in three quantities: model size N, training data size D, and compute C. As you scale these up, error keeps falling, but the rate of improvement slows down.

This is the opposite of linear improvement. To reduce error linearly by a small amount, you typically need to increase compute exponentially. This is the diminishing returns problem: doubling the model size does not double the performance gain, you get progressively less for each extra unit of compute.

Two influential papers debated the right balance. Kaplan et al. argued that for a given compute budget, model size N should grow faster than dataset size D. Hoffmann et al. (the Chinchilla paper) revised this: for a 10× compute increase, both N and D should grow, and the previous models were undertrained. GPT-3 with N = 175B and D = 300B was undertrained by Chinchilla standards, which is why newer models prioritise more tokens.

Despite diminishing returns, scaling unlocked emergent capabilities: behaviours such as multi-step reasoning, code generation, and in-context learning that suddenly appeared at certain model sizes. Vision faces a unique challenge: labels are sparse (one per image), so scaling vision needs denser learning signals, which is where SSL comes in.

Limits on scaling include exhausted high-quality human-generated training data, exponentially rising GPU and electricity cost for only linear gains, performance decay from training on AI-generated synthetic data, and structural problems like hallucinations that scaling alone cannot fix.

INTERMEDIATEExplain how MAE works and why a 75 percent masking ratio is the sweet spot.

Masked Autoencoders (MAE) by He et al. is a self-prediction pretext task for vision. The idea is to mask a random subset of image patches, encode only the visible patches through a ViT, then use a small decoder to reconstruct the missing patches from those visible features. The loss is mean squared error between predicted and actual pixel values in the masked regions.

The pipeline has three steps. First, divide the image into patches and randomly mask 75 percent of them. Second, run the visible 25 percent through a standard ViT encoder. Third, insert mask tokens as placeholders for the missing patches, run everything through a lightweight decoder, and compute the reconstruction loss only on the masked patches.

Why 75 percent? It is a careful balance between two failure modes. With a low mask ratio (say 25 percent), the model can solve the task by simple interpolation from nearby visible neighbours. That is a shortcut and the model never learns to reason globally. With too high a mask ratio (say 95 percent), there is not enough visible content for the model to recover the missing regions even with full understanding.

At 75 percent, the model is forced to use global reasoning. Local interpolation is impossible because most neighbours are masked, so the model has to build a coherent understanding of the whole image to fill in the gaps. This is what produces strong representations.

Random masking works better than block masking. Random masking spreads visible patches roughly evenly across the image, so the model gets a global hint. Block masking puts visible patches in one region and forces extrapolation, which is harder and less stable.

MAE generalises to audio. MAE-AST (MAE that listens) masks spectrogram patches and reconstructs them with the same recipe. MAE features are particularly good for localisation and counting tasks because reconstruction forces dense spatial information into the encoding.

INTERMEDIATEWhat is contrastive learning, why does it need large batches, and how does MoCo solve that?

Contrastive learning makes the model bring similar things together in embedding space and push dissimilar things apart. For an image x, you apply two random augmentations (crop, colour jitter, flip, blur) to produce two views x_1 and x_2. Both go through the encoder to produce embeddings z_1 and z_2. The InfoNCE loss is cross-entropy over cosine similarities: one positive pair (z_1, z_2) and many negatives (other images in the batch):

$$\mathcal{L} = -\log \frac{\exp\!\bigl(\text{sim}(z_1, z_2) / \tau\bigr)}{\sum_k \exp\!\bigl(\text{sim}(z_1, z_k) / \tau\bigr)}$$

SimCLR is the canonical version. It uses cosine similarity, adds a projection head (MLP) on top of the encoder during training (and discards it afterward), and treats every other sample in the batch as a negative.

Contrastive learning needs lots of negatives. With too few, the model collapses everything to a small region in embedding space (a trivial solution), and downstream performance suffers. The "manifold coverage" argument is that millions of instances act like millions of soft classes, so the model has to learn fine distinctions to separate them all.

The naive way to get many negatives is a huge batch size, often in the thousands. This is expensive: GPU memory and compute scale with batch size.

Momentum Contrast (MoCo) solves the same problem cheaply. Instead of recomputing all negatives every batch, MoCo maintains a FIFO queue of recently encoded samples that act as negatives. The queue is huge (could be insane sizes such as 65K), much larger than any practical batch.

But there is a subtlety: if you encode current and queued samples with the same online network, the queue contains "stale" representations that are inconsistent. MoCo introduces a momentum encoder, which is a slowly updated EMA copy of the main encoder, used to encode the queue. The momentum encoder is updated as θ_momentum = m · θ_momentum + (1-m) · θ_online, with m around 0.999. Stop-gradient is applied at the momentum branch.

This decouples queue size from batch size, gives consistent negative representations across the queue, and effectively gets you a massive contrastive batch without the memory cost. MoCo became the basis for DINO and many other teacher-student SSL methods.

ADVANCEDWalk through DINO step by step. Cover the student-teacher architecture, augmentations, centering, sharpening, EMA, and stop-gradient.

DINO (Self-Distillation with No Labels) is a teacher-student SSL method that removes explicit negatives. Two identical networks (student and teacher) are both Vision Transformers with a 3-layer MLP projection head. The projection head maps to an N-dimensional output space, default N = 65536 prototypes.

Augmentations: both student and teacher receive augmented views of the same image. The augmentation pipelines (p_s for student, p_t for teacher) share standard transforms such as random resized crop, colour jitter, horizontal flip, random grayscale, and Gaussian blur. The key difference is cropping scales:

  • Teacher receives only global crops (large-scale, covering more than 50 percent of the image, capturing overall context).
  • Student receives both global crops and local crops (small-scale, less than 50 percent of the image, sometimes only a fraction of an object).

This local-to-global asymmetry forces the student to deduce the teacher's holistic representation even when observing only a tiny patch.

Forward pass: each network tokenises image patches plus a [CLS] token, adds positional embedding, runs self-attention, and produces a [CLS] output through the projection head.

Teacher centering: the teacher's output first undergoes a centering operation: t ← t - C. C is a running mean of the teacher's output across the batch. Centering prevents dimension collapse, which is the failure mode where a single prototype dominates the softmax for every image (because we have no labels, the model could trivially put all images on one prototype and the loss would still go down).

Softmax with temperature: both outputs are converted to probability distributions via softmax(output / T). The student uses a standard temperature T_s. The teacher uses a lower temperature T_t < T_s, which is called sharpening. Sharpening creates a peakier, more confident distribution that the student can mimic. Centering alone leads to uniform lazy distributions, sharpening counters that. The two together balance diversity (centering) and confidence (sharpening).

Loss: cross-entropy between the student's distribution and the teacher's sharpened-centered distribution.

Student update: gradient descent on the cross-entropy loss.

Teacher update: not by gradients. Instead, EMA from the student: Θ_t = l · Θ_t + (1-l) · Θ_s with l around 0.99. This momentum update gives two benefits. Stability: if the teacher updated as fast as the student, the target would be a moving goalpost. Model ensembling: EMA aggregates the student over many iterations, acting as a temporal ensemble for more robust predictions.

Stop-gradient: applied at the teacher branch. Gradients flow only through the student during backprop. The teacher is updated separately via EMA.

DINO produces more universal patch representations than MAE. MAE features have higher variance components which hurt distance-based tasks like k-NN. Modern segmentation foundation models such as Segment Anything (SAM) use DINO features as the backbone.

EXPERTHow does I-JEPA combine MAE and DINO, and why is predicting in embedding space useful?

I-JEPA (Image-based Joint Embedding Predictive Architecture) combines the strengths of MAE and DINO. From MAE it takes the idea of masking a region and predicting it. From DINO it takes the idea of self-distillation with EMA targets. The crucial difference from MAE is that I-JEPA predicts in embedding space, not in pixel space.

Pipeline: split the image into patches. Visible patches go through the context encoder. Mask tokens (positional encodings) tell the predictor what to predict. A target encoder (an EMA of the context encoder) processes the full image and produces target embeddings for the masked region. The predictor takes the visible context and predicts the target embedding of the masked region. The loss is computed in embedding space.

Predicting in embedding space is useful for several reasons. First, the encoder can ignore low-level pixel details (textures, exact colours) and focus on semantic structure. MAE wastes capacity reconstructing pixels exactly, which forces the encoder to encode irrelevant details. Second, you can train at higher resolution effectively because the target is compressed. Third, the representations are more directly usable for downstream tasks that care about semantics, not pixels.

I-JEPA inherits two practical advantages. Like DINO it does not need negative samples. Like MAE it has dense learning signal because each masked patch contributes to the loss. The result is a strong foundation model with simpler training than contrastive methods and richer learning than pixel reconstruction.

The deeper philosophical point is that humans do not predict pixels, they predict abstract states. A baby learning to catch a ball does not reconstruct pixels of the future, it predicts that the ball will arrive at some location. I-JEPA is a step toward this kind of abstract prediction, which is the direction Yann LeCun has been advocating.

Multimodal Alignment

BEGINNERWhat is CLIP and how does it do zero-shot classification?

CLIP (Contrastive Language-Image Pretraining) is OpenAI's vision-language foundation model from 2021. It has two encoders: one for images (a Vision Transformer or ResNet) and one for text (a Transformer). Each encoder produces a single embedding vector. Both vectors are normalised so they live on a unit sphere.

CLIP is trained with a symmetric contrastive loss on 400M image-text pairs scraped from the web with their alt-text as captions. For a batch of N pairs, the loss maximises the cosine similarity of the N matched diagonal pairs (each image with its paired caption) and minimises the N(N-1) mismatched off-diagonal pairs. There are two directions: image-to-text and text-to-image, summed together.

After training, the image encoder and text encoder share an embedding space where matched images and captions land close together.

Zero-shot classification on a new dataset works without any training. For each class name, write a prompt such as "a photo of a {class}". Encode each prompt with the text encoder to get a class embedding. Encode the test image with the image encoder to get an image embedding. Compute cosine similarity between the image and each class embedding. The class with the highest similarity is the prediction.

This is powerful because you can reconfigure the classifier just by writing new text prompts. There is no retraining. CLIP can classify ImageNet, then EuroSAT, then food types, all from the same weights.

INTERMEDIATEWhy does text prompt design matter so much for CLIP, and what strategies improve it?

CLIP class labels live as text embeddings in a shared image-text space. Different prompts produce different embeddings, which produce different cosine similarities, which produce different predictions. So the prompt directly changes what CLIP thinks the classes look like.

"dog" alone gives an embedding for the abstract concept. "a photo of a dog" matches the distribution CLIP was trained on (alt-text from photos), so the embedding is closer to actual dog images. Empirically prompts that resemble natural captions perform much better.

CLIP often fails on certain language phenomena because it relies on similarity matching and co-occurrence statistics, not real linguistic understanding. Common failure cases:

  • Negation: "a girl wearing a dress that is not blue" versus "a girl wearing a yellow dress". CLIP cannot reliably handle negation.
  • Attribute binding: "a boy in black and a girl in white" versus "a girl in white and a boy in black". CLIP may mix up which attribute goes with which entity.
  • Relational reasoning: "a dog chasing a man" versus "a man chasing a dog". CLIP often cannot distinguish who is the subject and who is the object.

Strategies to improve prompts:

  1. Make prompts resemble natural captions. "a photo of a dog" is better than just "dog".
  2. Average multiple prompts to reduce single-wording bias. Ensemble 80 templates such as "a photo of a {}", "a picture of a {}", "an image showing a {}", and average the resulting text embeddings.
  3. Include attributes or scene details to be more specific. "a photo of a black dog running outdoors" gives more context than "a dog".
  4. Adapt prompts to the target domain. Medical imaging needs "a chest x-ray of...", satellite imagery needs "a satellite photo of...".

CoOp (Context Optimization) goes further: instead of hand-writing prompts, learn the context tokens with gradient descent on a small labelled set, keeping the rest of the CLIP weights frozen. Only the context tokens are updated, which is essentially prompt-based PEFT applied to multimodal models.

INTERMEDIATEWhat is the role of the temperature parameter in CLIP, and how is it chosen?

The temperature τ scales the similarity logits before the contrastive softmax. The contrastive loss looks like softmax(similarity / τ). Temperature controls how sharp or smooth the resulting probability distribution is.

A low temperature (small τ) makes the distribution sharp. The model focuses strongly on the most similar image-text pair and assigns near-zero probability to the rest. Gradients flow mostly through the top match.

A high temperature (large τ) makes the distribution smooth. Many pairs receive moderate probability. Gradients spread across many positions.

Both extremes hurt. Too low τ causes gradient instability because tiny changes in similarity flip which pair wins. Too high τ makes the loss weak because all pairs look similar to the model and there is little signal to separate matched from mismatched pairs.

In CLIP, the temperature is implemented as a learnable logit scale parameter (typically τ_init ≈ 0.07, expressed as a learnable log scalar that is initialised at log(1/0.07) and clamped). It is optimised via backpropagation during training, so the model itself finds the right balance between discrimination and stability. The learnable formulation also matches what was used in MoCo.

Side note for DINO: temperature plays a similar role but is asymmetric. The teacher uses a lower temperature than the student (sharpening) to provide a confident target. This is conceptually different from CLIP but mathematically uses the same softmax-with-temperature trick.

ADVANCEDCompare CLIP, CoCa, BLIP-2, and LLaVA in terms of architecture, training objective, and trade-offs.

These are the four representative paradigms of vision-language models covered in lecture 4.

CLIP (OpenAI, 2021) — Two-tower, alignment only. Separate image encoder and text encoder, no decoder. Trained with symmetric contrastive loss on 400M web image-caption pairs. Produces a shared embedding space. Excellent at zero-shot classification, retrieval, and open-vocabulary tasks. Cannot generate text. Cannot answer free-form questions about an image.

CoCa (Google, 2022) — Two-tower, alignment plus text decoder. Adds a text decoder on top of the image encoder. The image encoder produces patch features which feed two attention pooling modules: one with a single query for the global embedding (contrastive loss with text encoder), another with 256 queries for sequence-aware features (cross-attention for the text decoder, which generates captions autoregressively). Unifies contrastive alignment with generation. Strong on zero-shot classification, captioning, and VQA. Expensive to train because everything is jointly optimised.

BLIP-2 (Salesforce, 2023) — Two-leg, Q-Former plus frozen LLM. Reuses a frozen pretrained image encoder and a frozen pretrained LLM, training only a bridge module called the Q-Former. The Q-Former uses 32 learnable queries to extract image features via cross-attention with ViT outputs. Stage 1 trains the Q-Former alone with three objectives (contrastive, generation, matching). Stage 2 connects Q-Former outputs to the frozen LLM via a small projection. Only about 100M trainable parameters. Compute efficient and less forgetting because most weights stay frozen. Weakness: the Q-Former adds complexity and the M=32 token output may be a bottleneck.

LLaVA (Microsoft/UW, 2023) — Two-leg, MLP plus LLM. Even simpler than BLIP-2. The image features from CLIP ViT pass through a single MLP projection, then concatenate with text token embeddings into the LLM. Stage 1 trains only the MLP for image-caption alignment. Stage 2 fine-tunes the MLP and the LLM together on instruction-following data. The breakthrough is the data: 158K instruction-following multimodal samples generated by GPT-4 from image captions and bounding boxes. Strong conversational ability but originally weak on traditional VQA. LLaVA 1.5 fixed VQA with prompt formatting, a 2-layer MLP connector with GELU (1024 to 4096 to 4096), and 665K samples including OCRVQA, OKVQA, GQA, and ShareGPT.

The trajectory shows a clear arc. CLIP did alignment only. CoCa added generation. BLIP-2 made the architecture modular and efficient by freezing backbones. LLaVA simplified further and put the focus on data. Modern MLLMs such as LLaVA 1.5/1.6/Onevision, Qwen2-VL, and others build on the LLaVA paradigm with better connectors, resolutions, and data.

MLLMs and Visual Reasoning

INTERMEDIATEHow does LLaVA 1.5 differ from LLaVA 1.0, and why did those changes matter?

LLaVA 1.0 was strong at conversational visual reasoning but fell short on traditional visual QA benchmarks such as VQAv2 and GQA. The original model used a linear projection (one layer) as the connector and a relatively small dataset of 158K instruction-following samples.

LLaVA 1.5 made three targeted changes that turned it into a general-purpose visual assistant.

1. Prompt formatting. Different question types need different answer formats. Traditional VQA wants short answers, conversational visual reasoning wants longer detailed ones. LLaVA 1.5 adds explicit formatting prompts: for VQAv2 and GQA append "answer the question using a single word or phrase", for OKVQA (multiple choice) append "answer the option's letter from the given choices directly". This stops the model from rambling on a task that expects a one-word answer, which used to crush its benchmark scores.

2. Wider connector. The original linear projection was a bottleneck. LLaVA 1.5 replaces it with a two-layer MLP that uses GELU activation. The architecture is 1024 to 4096 to 4096 (CLIP ViT-L output to LLM hidden dim). The wider MLP gives the model more capacity to translate visual features into the LLM's representation space.

3. More and diverse data. The training set grew from 158K to 665K samples. Additions include VQA-v2 and GQA for short open-ended QA, OKVQA for multiple choice, OCRVQA for text-in-image, and ShareGPT for multilingual coverage (Spanish, Japanese, Korean, Chinese). Diversity matters because the original LLaVA was essentially CoCo plus GPT-4 generated dialogue, which biased it toward a narrow distribution.

The three changes together moved LLaVA from a strong conversational model with weak VQA into a balanced general-purpose visual assistant.

INTERMEDIATEWhat is the resolution compute trap in MLLMs, and how do LLaVA-HD, LLaVA-Next, and Qwen2-VL handle it?

CLIP ViT-L was trained at 224 by 224 or 336 by 336 resolution. Many real-world MLLM tasks need higher resolution: charts have small numbers, OCR needs fine detail, small objects matter for VQA. But naively going to higher resolution explodes compute because attention scales quadratically with the number of tokens, and image tokens scale with image area. This is the resolution compute trap.

LLaVA 1.5-HD: splits a 448 by 448 image into four 224 by 224 tiles, encodes each through CLIP ViT-L, and also encodes a resized full image as a global view. A special row-end token tells the LLM which tile sits where in the grid. This roughly quadruples the number of visual tokens and significantly alleviates hallucinations because the model can see fine detail. The downside is the extra tokens occupy LLM context.

Going too high hurts performance on OCR and small object understanding because attention spreads thin across too many tokens.

LLaVA-Next (LLaVA 1.6): preserves native aspect ratios by choosing from a set of grid layouts at 336 by various combinations such as (2,2), (1,2), (2,1), (1,3), (3,1), (1,4), (4,1). The system picks the closest matching grid for each image so portrait images use vertical grids and landscape images use horizontal grids, avoiding wasted compute on padding regions.

LLaVA-UHD: dynamically selects the best partition and uses a Q-Former-like compression to save compute. OCR improves significantly without new training data.

Qwen2-VL: takes a completely different route. The LLaVA paradigm has information redundancy and spatial collapse because 2D images get flattened into 1D sequences with absolute positions. Qwen2-VL uses Multimodal RoPE (M-RoPE) that factorises position into three components: time, height, and width. Each component gets its own RoPE rotation. This lets the model handle variable-length inputs natively and extrapolate to longer sequences at inference. It works for both images at any resolution and videos with multiple frames over time.

Other techniques worth knowing. Chain-of-Spot reasons about regions of interest, proactively zooming in on relevant areas. Zoom-Refine prompts the model to re-evaluate its initial answer using a zoomed crop and then combine with the original image to detect omissions.

ADVANCEDWhy is multimodal in-context learning difficult, and what factors affect it?

In-context learning (ICL) is the ability of a model to learn a new task from a few example input-output pairs in the prompt, without any parameter updates. For multimodal models, the examples can interleave images and text, which makes ICL very flexible. It is important because users can adapt the model on the fly without finetuning.

Multimodal ICL is harder than text-only ICL because three sources of sensitivity all matter.

1. Example order. Shuffling the order of just 4 examples can swing accuracy by 10 to 20 percent. Similar to LLMs, MLLMs favour the first and last positions, an effect called "lost in the middle". Examples in the middle of the context tend to receive less attention. This means the order in which you present examples can change your results dramatically.

2. Example relevance. Examples that are semantically close to the target question help much more than random examples. If you are testing the model on a chart-reading task, examples that involve similar charts give better results than examples about totally different content. Choosing relevant in-context examples is itself a retrieval problem.

3. Prompt structure. An introductory instruction before the examples improves performance. Telling the model "here are some examples of the task, then a new question" makes the pattern explicit. Without an introduction, the model has to infer the task purely from the example structure, which it does inconsistently.

Beyond these three, factors such as the number of examples, how images and text are interleaved, and whether the examples align with the answer format all play a role. Long-context MLLMs such as LLaVA-Onevision are designed to handle larger numbers of multimodal examples without losing focus, but the sensitivity to order and relevance persists.

The takeaway is that multimodal ICL works but it is brittle. For reliable deployment, you should curate examples carefully, use retrieval to pick examples relevant to each query, include a clear instruction, and validate that order does not flip your conclusions.

EXPERTWhy do unified multimodal models matter, and how does Janus-Pro avoid the pitfalls of fully unified architectures?

Up to LLaVA-Onevision and Qwen2-VL, MLLMs read pixels but cannot write them. They can describe an image but cannot generate one. Unified multimodal models try to handle both directions in one architecture so the model can understand visual input and produce visual output.

Why this matters: humans use non-verbal reasoning constantly. We mentally simulate physics, plan routes by visualising space, predict whether stacked objects will fall. Visual Simulation is critical to human non-verbal reasoning. If models are restricted to text-only outputs, they miss problems easier to solve by "thinking in pictures". The long-term vision is a truly omni-modal foundation model.

The straightforward approach is to use a single tokenizer for both modalities. Chameleon (Meta) does this: a discrete VQ tokenizer (8192-entry codebook) turns images into token IDs that look just like text tokens. A single Transformer with mixed-modal early fusion handles both. The simplicity is attractive but discrete VQ tokenizers lose lots of details, and next-token prediction is less effective for spatially structured images than for text.

Show-o is similar to Chameleon but observes the same problem. Unified models compromise on both fronts: they can understand and generate but are not as strong at either as specialised models.

Janus-Pro takes a different approach: decouple understanding from generation. For understanding, the model uses CLIP-style features that preserve semantic richness. For generation, it uses VQ Tokenizer features suited to discrete image synthesis. The two pipelines share a Transformer backbone but use different encoders and decoders. This separation lets each side use the representation best suited to its task.

The result is dramatic. Janus-Pro almost doubles the multimodal understanding performance of fully unified MLLMs while still supporting image generation. The lesson is that "unified" does not have to mean "single representation". Sharing a backbone while diverging at the input and output is a powerful compromise.

This decoupling also has analogies in other domains. Janus-style decoupling shows up in retrieval, where dense embeddings for one task and sparse representations for another can coexist over a shared model.

High-Dimensional Indexing

BEGINNERWhy do we need vector databases instead of traditional databases?

Traditional databases such as MySQL and PostgreSQL store structured data in rows and columns (user IDs, timestamps, prices) and rely on keyword matching for search. They are excellent for exact lookup but bad at understanding meaning.

Consider a help-desk chatbot. The user asks "my laptop crashed before submission, what should I do?" The relevant document is the assessment policy on extensions. There is no shared keyword: "crashed" does not match "extension", "laptop" does not match "policy". A traditional DB returns nothing useful.

A vector database works differently. Each document and each query is first encoded into a high-dimensional embedding by a neural network. In the embedding space, semantically related concepts land close to each other. "iPhone" and "Samsung" produce very similar vectors because they are both smartphones. "laptop crash before submission" produces a vector near "assessment extension for technical issues".

The core capability of a vector database is calculating distance. It finds the vectors closest to a query vector from millions of candidates within milliseconds. The standard metrics are cosine similarity (angle between vectors) and Euclidean distance (straight-line distance). The output is the top-k nearest neighbours.

This is why vector DBs are essential for RAG, semantic search, recommendation systems, and any AI application that needs to find conceptually related items rather than exact keyword matches.

INTERMEDIATEWhat is approximate nearest neighbour search, and why is it necessary at scale?

Exact k-NN search through a flat index is trivially correct: you compute the distance from the query to every stored vector and return the k smallest distances. The accuracy is perfect because you check everything. The cost is O(N) per query. For a database of 100 million vectors at 1000 dimensions in FP32, that is 100M × 1000 × 4 = 400 GB of data to scan per query. Even on a fast GPU, that takes seconds. For a search service that needs millisecond response times, this is unacceptable.

You might hope a tree structure like KD-tree solves it. In low dimensions, KD-trees split the space into hyper-rectangles and let you prune branches that cannot contain the nearest neighbour. But as dimension grows, the tree degenerates into something like a linear scan. The curse of dimensionality strikes again: in high dimensions, almost every cell contains a candidate that has to be checked, so pruning fails.

Approximate Nearest Neighbour (ANN) search relaxes the requirement. You return points whose distance is at most c times the true nearest distance for some constant c. You may miss the absolute nearest point but get something close. Accuracy is measured by recall@k: of the true top-k nearest neighbours, how many did your approximate search return?

ANN trades off three things: runtime (time per query), accuracy (recall), and memory consumption. You can move any pair of these to the worse side to gain on the third. Different ANN algorithms make different choices in this triangle.

Three main approaches. Partitioning (IVF) splits data into clusters and only searches the closest clusters. Quantization (Product Quantization) compresses each vector into a few bytes so distances are approximate but fast to compute by table lookup. Graph-based (HNSW) builds a navigable proximity graph and greedily walks toward the query. In production, IVF-PQ is common for billion-scale data and HNSW is popular for moderate-scale systems with high recall requirements.

ADVANCEDExplain how HNSW works and how its hierarchical structure differs from IVF.

HNSW (Hierarchical Navigable Small World) is a proximity graph for ANN search. Nodes are vectors. Edges connect vectors that are close to each other, typically by Euclidean distance.

To search, you start at a predefined entry point and walk along edges greedily. At each step, you look at the neighbours of the current node, find the one closest to the query, and move there. You stop when no neighbour is closer than the current node. The greedy walk usually finds an approximately nearest neighbour in logarithmic time, much faster than a linear scan.

The hierarchical part is borrowed from skip lists, a 1D data structure for fast search. The top layer has very few nodes spread far apart, like a coarse roadmap. Each lower layer has more nodes spaced more closely. The bottom layer (Layer 0) contains every vector. To search, you start at the top layer, do a greedy walk to find the local region, then drop down a layer and refine, and continue down to Layer 0 for the final nearest neighbour.

HNSW versus IVF:

  • IVF (partitioning): split the data into k clusters via k-means. To query, find the centroid closest to the query, search only the vectors in that cluster (and possibly some neighbouring clusters). The tunable parameters are nlist (number of clusters) and nprobe (how many clusters to check). Coarse but works well at very large scale, especially with Product Quantization (IVF-PQ).
  • HNSW (graph): build a multi-layer proximity graph. Query by greedy walk from the top down. Three tunable parameters: M (number of edges per node, controls memory and recall), efConstruction (search width during build), efSearch (search width during query). Higher numbers give better recall but slower search and more memory.

IVF tends to be more memory-efficient (you store the centroids and cluster membership, not graph edges) and good at very large scale (billion+). HNSW tends to give higher recall at lower latency for moderate scale (millions to low hundreds of millions of vectors) but uses more memory because of edge storage.

In practice, FAISS supports both IVF-PQ and HNSW. Milvus supports both plus annotation filters. Chroma uses HNSW under the hood. The right choice depends on data size, hardware, latency budget, and required recall.

INTERMEDIATECompare FAISS, Chroma, and Milvus. When would you pick each?

All three are popular vector tools but they live at different scales and complexity levels.

FAISS (Facebook AI Similarity Search): an open-source algorithm library from Meta. Not a standalone server software, but a Python and C++ library you import directly. Data is stored in RAM or saved as local files. Extremely fast and lightweight. The underlying engine for many higher-level vector DBs. Suitable for demos, local tools, and use cases under 100K vectors that fit in RAM. The API is low level: you build an index, add vectors with index.add, and search with index.search. Alternative distances supported include maximum inner product and L1 Manhattan.

Chroma: the SQLite of the AI era. AI-native, open-source, focused on developer experience. Can run locally in-memory (like FAISS) or be deployed as a server. The biggest selling point is simplicity. Strong metadata filtering, so you can search only documents where category equals finance. Good for 100K to 5M vectors. Suitable for MVPs and internal systems. Easy to set up with pip or Docker.

Milvus: enterprise-grade, cloud-native, distributed. Designed for large-scale and high reliability. Easily supports billions of vectors. Provides replicas, sharding, and disaster recovery. Maintains low latency even at massive scale. Suitable for enterprise production, massive knowledge bases (indexing all national news), and complex hybrid search. Hard to set up because it usually runs on Kubernetes.

Pick FAISS for prototyping and small scale, Chroma for application development at moderate scale, Milvus for production at enterprise scale. LangChain uses the VectorStore interface, so you can transition from Chroma in development to Milvus in production with minimal code changes. The data processing logic stays the same.

Two pitfalls regardless of choice. Dimension mismatch: if you change embedding models, the vector length changes (OpenAI 1536, HuggingFace 768), and you must re-index everything. Lock your embedding model at the start. Metadata performance trap: searching "2023 financial reports" can fail if the DB uses post-filtering (find top 100 vectors first then filter by date). Use pre-filtering so the date constraint applies before the vector search.

Token Reduction

BEGINNERWhy do we need token reduction, and what kinds of redundancy can we exploit?

The reason we need it is that self-attention scales quadratically with sequence length. For a vision-language model, the cost is proportional to (N_text + N_image) squared. Concrete example: with 200 text tokens, attention cost is 40K. Add 200 image tokens, cost goes to 160K, four times more. Add 800 image tokens, cost goes to 1M, twenty-five times more. Doubling image tokens leads to roughly 4× more compute. High-resolution images quickly dominate cost.

The good news is that there is real redundancy in image tokens that we can exploit. The course identifies three kinds.

First, irrelevant backgrounds or less informative tokens. The classic example is an image of a horse where the green pasture and blue sky take up most of the image. Removing background tokens, you can still classify the image correctly as a horse. The semantic content is concentrated in a small fraction of the patches.

Second, similar or duplicate tokens. Nearby patches in a smooth region (a clear sky, a wall) carry nearly identical features. Storing them all is wasteful, you can merge them into a single representative.

Third, noise. Some tokens carry information that hurts the task because the model gets distracted or overfits to spurious features.

These three motivate the four token reduction methods covered in lecture 7. Pruning removes irrelevant tokens. Merging combines similar tokens. Routing skips computation for some tokens. Resampling learns a compressed latent set from scratch. Each maps to a different kind of redundancy.

INTERMEDIATEWalk through the four token reduction methods and compare their pros and cons.

1. Token pruning. Z is a subset of X. Assign an importance score to each token and keep only the top-K. Importance can come from attention weights, gradient magnitudes, or learned MLP-based predictors. Examples: DynamicViT uses an MLP module to predict per-token importance from local and global features. EViT uses [CLS] attention averaged across heads. ATS maintains token scores and uses Inverse Transform Sampling on the cumulative distribution. Pros: straightforward, easy to interpret and visualise. Cons: irreversible information loss because removed tokens are gone forever, and you often need to finetune to recover performance.

2. Token merging. Z consists of merged tokens. Instead of dropping, you average or aggregate similar tokens into a fused representative. ToMe (Token Merging) is the canonical example. It splits tokens into Group A and Group B, computes cosine similarity for every cross-group pair, takes the top-K most similar pairs, and merges them with weights. The attention later uses a modified softmax that accounts for the merged token volume: A = softmax(QK^T/√d_k + log s). Pros: smoother performance degradation than pruning, preserves information, usually finetuning-free. Cons: merging blurs distinctions that matter for fine-grained tasks (merging "cat ear" and "dog ear" gives ambiguous "animal ear"), and finding similar tokens is expensive for long sequences.

3. Token routing. Z can include previously unselected tokens. A learned router decides per token whether to compute, skip, or aggregate at each layer. IdleViT re-selects tokens that were inattentive in shallow layers, since a token might be unimportant early but become critical later. MoD (Mixture-of-Depths) uses a router to decide whether each token bypasses a layer. Evo-ViT splits tokens by accumulated attention into a slow-update group and a fast-update group. Pros: information is preserved (only compute is skipped) and dynamic compute allocation is possible. Cons: increased hallucination risk and memory overhead for cached tokens.

4. Token resampling. Z learns from X. A small set of latent queries pulls information from the input. Perceiver uses cross-attention: Z = softmax(Q_q K_X^T / √d_k) V_X + Q_q, where Q_q are learnable queries of small size. Flamingo's Perceiver resampler reduces image tokens to just 64. BLIP-2's Q-Former is essentially a resampler that reduces a 257-token ViT output to 32 tokens. Pros: high compression ratio, end-to-end trainable, preserves semantics well. Cons: extra architectural complexity and parameters, needs finetuning or retraining.

You can combine methods. PPT prunes inattentive tokens (likely noise) and merges duplicative ones (redundant signal). ToFu prunes in shallow layers where features are coarse and merges in deep layers where fine-grained patterns matter. Token routing is the most general view: pruning and merging are special cases where tokens are never re-used.

ADVANCEDExplain the information bottleneck and how it interprets the different token reduction methods.

The information bottleneck (IB) is a theoretical principle from Tishby et al. The goal is to learn a compressed representation Z of input X that retains maximum information about a target Y. The objective is:

$$\min_{p(z|x)}\; I(X; Z) - \beta \cdot I(Z; Y)$$

I(X; Z) is the mutual information between input and compressed representation, which we minimise to compress. I(Z; Y) is the mutual information between compressed representation and target, which we maximise to retain accuracy. β is a Lagrange multiplier controlling the trade-off. A small β prioritises compression, a large β prioritises accuracy.

This is a beautiful unifying lens for token reduction. The four methods correspond to four IB strategies:

  • Pruning is a hard bottleneck. Discrete retention decisions. Z is literally a subset of X, with binary selection at each token: keep or drop.
  • Merging is a soft bottleneck. Weighted aggregation. Instead of discarding information, it performs local lossy compression by mapping multiple input points X_i and X_j to a single representation Z_k. The compression is smooth.
  • Routing is an adaptive bottleneck. Conditioned on the input. Not all tokens require the same amount of processing. Computation is treated as a finite resource. A router learns which tokens are information-rich and need the full depth, and which are predictable and can bypass layers.
  • Resampling is a latent bottleneck. A shorter latent query vector. It attempts to find a distribution of Z that best approximates the density of the most relevant features in X. Particularly useful for long-context or multimodal models where you need a fixed-size representation from variable-length input.

From the information strategy perspective: pruning is elimination, merging is aggregation, routing is adaptation, resampling is summarisation.

The key insight from IB theory is that two methods can compress equally well but yield very different downstream performance. A good method maximises I(Z; Y) while minimising I(Z; X), preserving predictive structure. A bad method minimises I(Z; X) but also drops I(Z; Y), keeping irrelevant detail. Compression ratio is not the same as quality of retained information. When choosing or designing a token reduction method, you want to keep the bits about Y, not just any bits about X.

Multimodal RAG

BEGINNERWhat is RAG and why do we need it?

RAG stands for Retrieval-Augmented Generation. The idea is to augment an LLM's response with relevant external knowledge retrieved at query time, instead of relying only on what the model memorised during training.

RAG matters because of four problems with bare LLMs:

  1. Static knowledge. LLM knowledge is frozen at the time of training. A model trained in 2024 does not know about events in 2025 unless you retrain it.
  2. Hallucinations. LLMs predict the next word based on the previous words. When they do not know something, they often produce plausible but incorrect answers because the most fluent continuation is not always the most accurate one.
  3. Cost and complexity. Retraining or fine-tuning to add new knowledge requires millions of new examples and significant compute. RAG is in-context learning: you just add new documents and the model can use them immediately.
  4. Context window. You cannot just feed all your knowledge into the prompt because context windows are limited and grow expensive quadratically. Context management matters more than the model itself in many real applications.

The naive RAG pipeline has three stages. Chunking: split documents into manageable pieces. Retrieval: find the top-k relevant chunks for a query using vector similarity search. Generation: feed the retrieved chunks plus the query to an LLM to produce the answer. All three stages can fail, which is why advanced RAG techniques exist.

INTERMEDIATEWhere can naive RAG go wrong, and what are the chunking strategies that address those failures?

Naive RAG has three classic failure modes.

  1. Broken chunks. Fixed-size splitting cuts ideas mid-sentence, leaving a paragraph that ends mid-thought and a continuation that lacks context. The retriever then matches fragments rather than complete ideas.
  2. Irrelevant documents. The retriever returns chunks that look semantically similar to the query but do not actually contain the answer.
  3. Wrong conclusion. Even with correct evidence, the generator may ignore retrieved context, over-trust its priors, or hallucinate.

Chunking strategies in order of sophistication:

  • Fixed-size chunking. Just split every N tokens. Straightforward but may split mid-sentence and lose context.
  • Recursive chunking. More structured. Start with section boundaries, drop into smaller units (paragraphs, sentences, words) only if too large. LangChain's RecursiveCharacterTextSplitter is the default for many systems.
  • Semantic chunking. Focus on meaning. Analyse semantic relationships between sentences and determine where the topic changes, then split at topic boundaries. Computationally expensive because you must embed and compare every adjacent pair.
  • Agentic chunking. Let an LLM decide where to split. Most flexible but expensive in tokens.

Practical sizing. The maximum chunk size is bounded by the embedding model (BERT 512 tokens, text-embedding-3 8192 tokens). Recommended is 250 to 512 tokens for general documents and 500 to 1000 for legal documents. Overlap is 10 to 20 percent generally, 25 percent for technical docs. Overlap helps when a chunk boundary cuts something important: the next chunk repeats enough that the idea is recoverable.

Even with good chunking, embeddings can miss exact identifiers such as error codes or part numbers. That is where BM25 and hybrid search come in.

INTERMEDIATEWhat is BM25 and why does Anthropic's Contextual Retrieval combine it with embeddings?

BM25 is a sparse, bag-of-words retrieval function. It ranks documents based on how query terms appear in each document, combining Term Frequency (TF) and Inverse Document Frequency (IDF) with two refinements.

First refinement: TF saturates. Early occurrences of a term in a document signal topic relevance, but later occurrences add little new information. BM25 uses a saturating TF function controlled by parameter k_1.

Second refinement: document length normalisation. Long documents naturally contain more occurrences of any term, so we normalise by length using parameter b. The full formula:

$$\text{score}(D, Q) = \sum_{i} \text{IDF}(q_i) \cdot \frac{\text{tf} \cdot (k_1 + 1)}{\text{tf} + k_1 \cdot \bigl(1 - b + b \cdot \tfrac{|D|}{\text{avgdl}}\bigr)}$$

Tuning: k_1 in [1.2, 2.0]. Smaller k_1 means documents are noisy or repetitive (saturate faster). Larger k_1 means documents are short and TF is a strong signal. b in [0.3, 0.9]. Smaller b means stronger penalty for long documents.

Why combine BM25 with embeddings? They have complementary strengths and weaknesses. Suppose a user queries "Error code TS-999" in a technical support database. An embedding model knows the query is about error codes in general but may miss the specific code "TS-999" because that string did not appear often during training. BM25 does exact text-string matching, so it finds the exact code instantly. But BM25 cannot understand paraphrases or synonyms, while embeddings can.

Anthropic's Contextual Retrieval pipeline:

  1. Break the knowledge base into chunks of a few hundred tokens.
  2. Create both TF-IDF encodings and semantic embeddings for each chunk.
  3. Use BM25 to find top chunks based on exact matches.
  4. Use embeddings to find top chunks based on semantic similarity.
  5. Combine and deduplicate the two lists using a rank fusion technique such as Reciprocal Rank Fusion.
  6. Add the top-k chunks to the prompt to generate the response.

Anthropic also adds another trick: before embedding each chunk, they use an LLM to prepend a short contextual prefix. For example, the chunk "The company's revenue grew by 3% over the previous quarter." becomes "The company is growing fast... The company's revenue grew by 3% over the previous quarter." The added context helps the embedding because the embedder sees who is being discussed.

ADVANCEDWhat are rerankers and Reciprocal Rank Fusion, and when would you use each?

After initial retrieval, you have a candidate list of chunks ranked by similarity score. Sometimes that ranking is good enough, but often the top results are missing the truly best matches that sit lower in the list. Rerankers and rank fusion are two ways to improve this.

Rerankers. A reranker is a more expensive model that re-scores the top candidates with a richer interaction between query and document. Initial retrieval uses cheap single-vector cosine similarity. A reranker takes (query, document) pairs and produces a relevance score using a cross-encoder, which lets the model attend to both query and document together. The result is more accurate ranking at the cost of more compute.

Popular rerankers: Cohere Rerank API, BGE-Reranker (open source), RankGPT (uses an LLM such as GPT-4 to do zero-shot listwise reranking with a sliding window for long candidate lists). Empirically, rerankers improve hit rate and Mean Reciprocal Rank across all embedding models.

The trade-off: rerankers are slower than retrieval, so you can only afford to rerank the top 20 to 100 candidates from initial retrieval. Recall before reranking still matters.

Reciprocal Rank Fusion (RRF). If you do not want to train or pay for a separate reranker, RRF combines ranked lists from multiple retrievers using rank positions rather than raw scores. The formula:

$$\text{RRF}(d) = \sum_{i} \frac{1}{k + \text{rank}_i(d)}, \qquad k \approx 60$$

For each document, sum up 1/(k + rank) across all retrievers that returned it. Higher RRF score means better fused rank. The constant k smooths the scores so that the difference between rank 1 and rank 2 is similar to the difference between rank 100 and rank 101.

Why RRF works. Different retrievers (BM25, embeddings, ColPali) have different strengths and different score scales. Raw scores cannot be averaged because BM25 might return 12.4 and a cosine similarity 0.87. Using rank positions normalises the scale and makes the combination robust. RRF outperforms Condorcet and individual rank-learning methods.

When to use which. Use a reranker when accuracy matters more than latency and you can afford the compute. Use RRF when you have multiple retrievers (hybrid search) and want a cheap robust way to combine them. The two compose: do hybrid retrieval with RRF, then rerank the top fused results with a cross-encoder for the best accuracy.

ADVANCEDTrace the MRAG evolution from 1.0 to 3.0 with concrete examples.

Multimodal RAG has gone through three generations of architecture, each more end-to-end than the last.

MRAG 1.0 (pseudo-MRAG). Convert images, tables, and other media into captions or OCR text, then run text-only RAG. Example: a PDF report has a bar chart. You run OCR over the numbers, generate a caption like "Bar chart showing revenue 2020-2024 with peak in 2023", and embed the text. At query time you retrieve the text and feed it to an LLM. Easy to build because the entire pipeline is text-based and the LLM does not need to be multimodal. Downsides: modality conversion causes information loss (subtle visual cues, spatial layout, chart trends), the retrieval bottleneck is in the conversion quality, and answers cannot reference the original visual.

MRAG 2.0 (true multimodal). Preserve the original multimodal data in the knowledge base. Support multimodal retrieval (image queries can find image chunks, text queries can find image chunks). Use an MLLM to generate answers directly from multimodal evidence. Example: a query about an image-only diagram in a manual can retrieve the diagram directly and feed it to an MLLM that reasons over the picture. ColPali is the canonical MRAG 2.0 system. Performance bottleneck in industrial RAG is usually in the data ingestion pipeline (parsing dirty PDFs), not in embeddings. ColPali sidesteps parsing entirely by embedding page screenshots directly with PaliGemma (a VLM with the LM head removed and trained contrastively). Late interaction (multi-vector matching with per-token max similarity) catches fine-grained matches.

MRAG 3.0 (end-to-end). Move toward fully multimodal pipelines with document screenshots, page-level representations, multimodal search planning, and multimodal outputs instead of text-only answers. Agentic RAG falls in this generation. The system decides which tool to use (text search, image search, OCR, structured query) and whether re-retrieval is needed. Search-o1 is an agentic search-enhanced reasoning model. VISOR does iterative search and over-horizon reasoning with visual evidence. DeepResearch-style systems plan multi-step retrieval where each result informs the next query.

What works in practice (ViDoRe V3 study). Visual retrievers outperform textual ones even when the query is text-only. Text rerankers outperform visual ones. Hybrid retrieval performs best by F1 (concatenate top-5 from visual and textual retrievers without deduplication). Image-based context outperforms text-based context because images provide visual cues for grounding. Charts, layouts, and figures are the hardest question types.

Andrej Karpathy's "LLM Wiki" is an alternative philosophy. Some knowledge is stable and frequently used, so it should be compiled into the model rather than retrieved every time. Long-frequency information that changes over time stays in RAG. Stable evergreen facts go in LLM Wiki. Future systems are hybrid: retrieve fresh raw evidence and compile stable reusable knowledge.

INTERMEDIATEHow does ColPali work and what is late interaction?

ColPali is a representative MRAG 2.0 system that addresses the parsing problem in document retrieval. The classic challenge is that real-world PDFs contain tables, charts, math, layout structures, and figures that text-based parsing pipelines mangle. Even modern OCR fails on dense or complex documents.

ColPali's idea: skip parsing entirely. Embed page screenshots directly with a Vision Language Model. The encoder is PaliGemma (a VLM by Google) fine-tuned to produce embeddings instead of generating text. The language modelling head is removed, and the model is trained contrastively (like CLIP) on (query, page-screenshot) pairs.

This means each page is represented as a sequence of visual token embeddings, one per visual patch. The query is also encoded as a sequence of text token embeddings. The key innovation is how matching works between these two sequences.

Late interaction. Instead of pooling the page into a single vector (early interaction or single-vector representation), ColPali keeps all the patch embeddings. At query time, for each query token, find the maximum similarity over all page tokens (max-sim), then sum those max-sims across all query tokens. This gives a fine-grained match: each query token finds its best matching visual location on the page, and the total score captures how many query tokens have strong visual support.

$$\text{score}(Q, P) = \sum_{i} \max_{j}\; \text{sim}(q_i, p_j)$$

Late interaction is the middle step between embedding and full reranking. Single-vector embeddings are fast but coarse. Full cross-encoder reranking is slow but precise. Multi-vector late interaction is in between: more accurate than single-vector, cheaper than cross-encoder.

Trade-offs of late interaction: you store many more vectors per page (one per patch), so memory cost is higher. You compute max-sim over all pairs at query time, so latency is higher than single-vector. The benefit is much better recall on visually complex documents where details matter.

ViDoRe V3 evaluation confirms ColPali outperforms MRAG 1.0 (OCR-based pipelines) thanks to late interaction. The performance is even stronger when you combine ColPali retrieval with text-based reranking.

ADVANCEDWhat is the modality gap and the cone effect, and how does Jina-Embeddings-v4 address them?

Contrastive multimodal training can create a bias known as the cone effect. Each modality (image, text) initially forms its own cluster in embedding space, because images and text have different feature distributions. Training pulls matched cross-modal pairs together with a contrastive loss. But instead of fully mixing the modalities, the embeddings form a high-dimensional cone-like bridge: the modalities stay somewhat separate, with alignment happening through a structured connection rather than a uniform shared space.

The modality gap shows up clearly when you examine the distribution of pairwise cosine similarities. Matching image-text pairs land near a certain similarity. Matching text-text pairs land at a different (usually higher) similarity. The gap between these distributions is the modality gap. OpenAI CLIP exhibits this gap clearly.

Why is this a problem? In MRAG, you want to query with text and retrieve images, or query with images and retrieve text. If the modalities are not truly mixed in embedding space, cross-modal retrieval is suboptimal. The matched image-text similarities are lower than they should be, and the rankings can be unstable.

Jina-Embeddings-v4 is a 3B parameter universal embedding model designed to reduce this gap. It supports both single-vector outputs (truncated to 128-dim if needed) and multi-vector outputs (N tokens of 2048-dim) for late interaction. The model uses Multimodal RoPE and is trained with PEFT, so the 3B base stays mostly frozen and only 60M parameters are PEFT-trainable.

Jina's multi-vector representation reduces the modality gap compared to OpenAI CLIP because per-token matching gives more flexible alignment than pooling everything into one vector. For OCR-heavy document retrieval, OCR plus BM25 still does better than CLIP-based single-vector retrieval, but ColPali (multi-vector with late interaction) beats both. Jina-v4 essentially combines the lessons: a strong base VLM, multi-vector outputs, and contrastive training, with PEFT to keep training affordable.

The practical takeaway is that single-vector embedding is the simplest and cheapest but suffers from the cone effect. Multi-vector late interaction reduces the gap and gives better cross-modal retrieval at the cost of more memory and compute.

RAG Evaluation

BEGINNERWhat metrics do we use to evaluate retrieval in RAG, and what does each measure?

Retrieval evaluation is the first layer of MRAG evaluation. The metrics split into two groups based on whether they consider rank order.

Non-rank-based metrics (binary outcomes):

  • Precision: the fraction of retrieved documents that are relevant. If you retrieve 10 documents and 7 are relevant, precision is 0.7. Answers "of what I returned, how much is useful?"
  • Recall: the fraction of relevant documents that are retrieved. If there are 8 truly relevant documents in the corpus and you found 5 of them, recall is 5/8 = 0.625. Answers "of what exists, how much did I find?"
  • F1: the harmonic mean of precision and recall. Balances the two. Notice that recall alone is easy to cheat by increasing k (return more documents); precision and F1 punish you for false positives.

Rank-based metrics (order matters):

  • Mean Reciprocal Rank (MRR): the average of 1/rank for the first relevant answer across queries. If the first relevant document is at rank 1, contribution is 1. At rank 5, contribution is 0.2. Answers "how early is the first relevant result?"
  • nDCG@K (Normalised Discounted Cumulative Gain): designed for graded (non-binary) relevance. DCG@K = Σ (2^rel_i - 1) / log_2(i+1). Items further down the list contribute less because of the logarithmic discount. nDCG normalises by IDCG (DCG of the ideal ranking) so it ranges 0 to 1. Answers "are the most relevant results ranked highest?"

When ground-truth documents are not available, you fall back to context relevance: does the retrieved document help answer the query? Two ways to measure: human annotation (taxing but aligns with human judgment) or LLM-as-a-judge (cheap, scalable, uses direct prompting or prompting plus in-context learning).

INTERMEDIATEWhat is the RAG Triad, and why is faithfulness/groundedness important?

Retrieval is necessary but not sufficient. Correct evidence can still lead to incorrect answers because the generator may ignore evidence, over-trust priors, or fuse modalities badly. The RAG Triad (from TruLens) breaks evaluation into three connected layers.

  1. Context Relevance: is the retrieved context relevant to the query? This is the retrieval evaluation question. Measured by Recall@k, Context Recall, nDCG@K, MRR.
  2. Answer Relevance / Answer Accuracy: does the generated answer actually address the user's question? Measured by comparing the answer to the question, often using LLM-as-a-judge. Does the answer talk about the right thing, regardless of whether it is correct?
  3. Groundedness / Faithfulness: are the claims in the answer supported by the retrieved context? This is the key check against hallucinations. Even if context is relevant and the answer addresses the question, the answer might add unsupported details.

Faithfulness is the most important and most subtle of the three. The standard approach uses LLM-as-a-judge with reverse engineering and decomposition. You decompose the answer into atomic claims ("the company's revenue grew by 3 percent", "Q3 was the peak", and so on), and for each claim, you ask the judge LLM whether the retrieved context supports it. The faithfulness score is the fraction of supported claims.

Why faithfulness matters more than correctness in many practical settings: a faithful but wrong answer is recoverable because you can verify against the cited context. An unfaithful answer, even if correct, is dangerous because it shows the model is making things up regardless of context, and that means next time it might be wrong without you knowing.

RAGAs, TruLens, and DeepEval are three popular frameworks that implement the triad. RAGAs uses LLM-based decomposition. FactScore generalises faithfulness to atomic-claim scoring. DeepEval combines several metrics with custom evaluators.

ADVANCEDWhy does text-centric evaluation fail in multimodal RAG, and what is query grounding?

Text-centric evaluation works when the entire RAG pipeline operates over text. Context relevance is measured by text similarity to the query. Faithfulness is measured by checking text claims against retrieved text. This breaks down badly when images are involved.

Consider a multimodal RAG system for radiology. The query is a chest X-ray plus a question. The retriever finds a similar-looking case from a database. The MLLM produces a diagnosis. How do you evaluate?

If you evaluate context relevance from the text perspective only, you compare the textual diagnosis from the retrieved case to the text query. The retrieved diagnosis might look plausible because the retriever pulled cases with similar text descriptions. The text query is just a question, so the comparison says it is relevant.

If you evaluate context relevance from the image perspective using CLIP-style similarity, you compare the query image to the retrieved image. Cosine similarity can be high because the two X-rays look superficially similar (same anatomy, same view). But high cosine similarity does not guarantee the right diagnosis. Two X-rays can look similar but show clinically different conditions.

The retrieved context is therefore wrong, the model produces a wrong diagnosis based on it, but text-centric evaluation passes because the text-only checks succeed. Text-centric evaluation fails in multimodal settings because it cannot ground claims in actual visual content.

Query grounding is the solution. A VLM or MLLM that grounds claims in the actual visual content checks whether the answer's visual claims are supported by what is actually in the image. This is similar to faithfulness checking but for the visual modality. Unfortunately, query grounding tools are still developing. Pure text-centric evaluation tools cannot do this, so you need multimodal evaluators or human raters.

Hallucinations in MRAG break down into five types: query-grounding hallucination (misreads the user-provided image), retrieval hallucination (answer fills in facts because evidence was not retrieved), grounding hallucination (evidence retrieved but visually misperceived), reasoning hallucination (combines facts from multiple sources into a false conclusion), citation hallucination (claim is true but cited source does not support it). MiRAGE assesses these in multimodal reasoning chains at the level of intermediate steps, not just final answers.

ADVANCEDExplain Visual Contrastive Decoding (VCD) and how it mitigates hallucinations.

VCD is a training-free method to mitigate object hallucinations in large vision-language models. It addresses the root cause: when visual evidence is weak, LVLMs over-rely on language priors and statistical biases learned during training. They learn spurious associations such as "scenes that look like beaches usually contain umbrellas", which leads to predictions of objects that are not actually in the image.

The VCD idea is to contrast the model's output distribution on the original image versus a distorted version of the same image. The intuition: the part of the output that survives both distributions is what the language model produces regardless of the visual input (the language prior). The part that comes only from the original image is the genuine visual contribution. Subtracting the noisy distribution removes the prior bias.

The pipeline:

  1. Given an image and a prompt, compute the next-token distribution: logits_original = LVLM(image, prompt).
  2. Apply Gaussian noise to the image to create a distorted version. Compute logits_noisy = LVLM(noisy_image, prompt). The noisy image carries minimal visual information, so the output reflects the language prior.
  3. Compute the VCD logits as: logits_VCD = (1+α) · logits_original - α · logits_noisy.
  4. Apply softmax to get the final probability distribution.

The contrast subtracts away parts of the distribution that the model would have predicted from text priors alone, sharpening the signal from the actual image. The result is fewer hallucinated objects and better grounding.

The α parameter controls how aggressive the contrast is. A small α has little effect, a large α can over-correct and start dropping legitimate predictions. Typical values are around 1.

VCD is appealing because it requires no extra training. You can drop it into an existing LVLM at inference time. The cost is doubled compute per token (two forward passes), but for high-stakes applications such as medical imaging or factual reporting, the trade-off is worth it.

VCD is self-correcting in spirit: it forces the model to commit to predictions that the image genuinely supports rather than predictions the prior would produce. For more aggressive mitigation, you can go beyond training-free methods and use RL (DPO with hallucination-aware preferences) to fine-tune the model to prefer grounded outputs over hallucinated ones.

Agents

BEGINNERWhat is an agent, and how does it differ from a plain LLM?

A plain LLM is a function: input text in, output text out. It can reason, write, summarise, and answer questions, but it cannot do anything beyond producing text.

An agent is a task-solving system that uses an LLM (or MLLM) to direct its own processes and tool usage. The agent can plan, use tools, access external data, and act across digital environments. Where a plain LLM stops at producing text, an agent uses that text as a sequence of decisions about what to do next.

In reinforcement learning terminology, an agent is an intelligent system that learns actions through interaction with an environment. The environment can be physical (robots, autonomous cars) or digital (Atari games for DQN, the Go board for AlphaGo, Apple devices for Siri). The agent perceives the environment, decides on an action, executes it, observes the result, and continues.

A language agent extends this idea using an LLM as the decision-maker. The action space includes internal actions (reason, plan, reflect), information actions (retrieve, search, query a database), and tool actions (call APIs, run code, generate charts). The reasoning, planning, memory (short-term in-context plus long-term vector store), and tools all wrap around an LLM core.

A common example: a chatbot that can answer a question using Wikipedia tools and calculator tools rather than just relying on its own training. When the user asks "what is the population of Brazil times the GDP of Norway?", the agent decides to look up two facts, fetch them with tools, multiply them with a calculator tool, then write the answer. Without tools, the LLM would guess from its training data and likely be wrong.

INTERMEDIATEExplain the ReAct framework and why interleaving reasoning with acting helps.

ReAct stands for Reasoning plus Acting. It is a prompting framework that interleaves language-based reasoning with external actions, instead of producing a single-shot final answer. The agent follows a loop: Thought → Action → Observation → Thought → Action → ... and so on, until it has a final answer.

Each step:

  • Thought: the model writes a short reasoning step describing what it knows so far and what to do next.
  • Action: the model calls a tool, such as a search engine, a calculator, or a database query.
  • Observation: the model receives the result of the action from the environment.

Why interleaving helps. Reasoning guides acting: the agent decides which tool to call based on what it has reasoned. Acting guides reasoning: new observations let the model revise its plan and correct earlier assumptions. Pure reasoning without acting is single-shot and prone to hallucination, especially for multi-step tasks where the model cannot verify facts. Pure acting without reasoning is mechanical and cannot adapt when an action returns unexpected results.

Concrete example in an embodied AI environment (ALFWorld). Task: heat some apple and put it in the fridge. The agent reasons: "I need to find an apple first". Action: go to kitchen counter. Observation: counter empty. Reasoning: "the apple must be in the fridge". Action: open fridge. Observation: apple in fridge. Reasoning: "now I need to heat it, the microwave is on the counter". Action: take apple, go to microwave, heat. The agent recovers from a wrong initial assumption (apple on counter) because of the observation.

ReAct is often more reliable than a single-shot LLM answer for multi-step tasks because the model can gather external evidence, revise its plan, and correct earlier assumptions. This reduces unsupported guessing and hallucinations.

The action space matters too. JSON function calling restricts you to predefined tools. A unified action space using Python code lets the agent write arbitrary code at runtime, which is far more expressive. The reasoning is also flexible: operational (track research status, check facts) in technical tasks, narrative or social (reflect intention, infer impressions) in interaction tasks. Unlike traditional game actions like jump or move left, agent actions include thoughts, plans, reflections, fact checks, and tool-selection rationales.

INTERMEDIATEWhat are self-consistency and Tree of Thoughts, and when does each help?

Both are inference-time methods to improve reasoning. They sit on top of the LLM and do not change the weights.

Self-consistency. Chain-of-Thought usually follows one greedy decoding path: at each step, take the highest-probability token. Self-consistency samples multiple greedy decoding paths (using temperature or stochastic decoding), extracts the final answer from each path, and majority votes. The intuition is that correct answers tend to be reached via multiple reasoning paths while incorrect ones diverge into different wrong answers. Aggregation by majority vote averages out the noise.

When self-consistency helps: tasks with a clear final answer (math problems, multiple choice, single-output classification) where you can group paths by their final answer and count. It does not help as much for open-ended generation tasks because the outputs are unique.

Tree of Thoughts (ToT). ToT goes further by treating each intermediate thought as a search state. Instead of just sampling final answers, the algorithm explicitly searches over intermediate reasoning steps.

  1. Sample or propose multiple candidate thoughts at each step. "Thoughts" can be paragraphs (creative writing) or words/equations (math). Use higher temperature or explicit prompting like "list several plausible next steps".
  2. Evaluate which thoughts are promising. Use a heuristic or an LLM evaluator to score states.
  3. Search over reasoning paths using BFS or DFS. BFS maintains a set of b (b ≤ 5) most promising states per step. DFS explores the most promising state first until the final output is reached, otherwise prunes subtrees.

The classic worked example is Game of 24: given four numbers, use arithmetic to make 24. ToT can backtrack when a partial expression looks unpromising.

When ToT helps: tasks that benefit from deliberate, structured exploration of intermediate states, especially problems where a wrong step early is hard to recover from. CoT and self-consistency are linear (one path at a time). ToT is hierarchical (multiple paths, with pruning and backtracking).

Both are prompting-level interventions. They control reasoning at inference time but do not change the model's underlying policy. For more reliable behavioural changes, you need post-training methods such as DPO and GRPO.

ADVANCEDWalk through RLHF, PPO, and DPO. What makes DPO simpler than PPO?

RLHF (Reinforcement Learning from Human Feedback) is the framework used to align LLMs to human preferences. Many real-world goals are hard to write as an explicit reward function. Worse, bad rewards lead to reward hacking, where the model finds a loophole that maximises the reward but produces bad outputs. RLHF replaces the reward function with human judgment as the signal.

The standard RLHF pipeline has three stages:

  1. SFT (Supervised Fine-Tuning): start from a pretrained LLM, fine-tune it on curated instruction-response pairs to get a baseline policy that knows how to follow instructions.
  2. Reward modelling: collect human preference data. For each prompt, ask humans to compare pairs of model outputs and pick the better one. Train a reward predictor r using the Bradley-Terry logistic preference loss, so r(preferred) ends up higher than r(rejected).
  3. RL fine-tuning: use the reward model as the reward signal and fine-tune the policy via PPO. A KL divergence term against the reference (SFT) policy prevents the policy from drifting too far.

PPO (Proximal Policy Optimization). PPO penalises the policy for changing too much between updates, because we already have a reasonable policy from SFT. The objective uses a likelihood ratio r(θ) = π_new / π_old that measures how much the new policy disagrees with the old, multiplied by an advantage function A (whether the action contributed to a better-than-expected reward). The ratio is clipped to prevent large swings:

$$\mathcal{L}_{\text{PPO}} = \mathbb{E}\!\left[\min\!\bigl(r(\theta)\,A,\ \text{clip}(r(\theta), 1-\varepsilon, 1+\varepsilon)\,A\bigr)\right] - \beta \cdot \text{KL}(\pi_\theta \,\|\, \pi_{\text{ref}})$$

PPO needs a separate value model that estimates the expected future reward at every state. The value model is itself trained alongside the policy. This is expensive: every state of every trajectory must be evaluated.

DPO (Direct Preference Optimization). DPO eliminates the explicit reward model and the value model entirely. The key mathematical insight is that when you substitute the optimal reward (derived from preferences) into the RL objective, the log Z(x) partition function cancels because the loss only cares about differences in rewards. So you can optimise the policy directly on (preferred, rejected) preference pairs:

$$\mathcal{L}_{\text{DPO}} = -\log \sigma\!\left(\beta \left[\log \frac{\pi_\theta(y_w | x)}{\pi_{\text{ref}}(y_w | x)} - \log \frac{\pi_\theta(y_l | x)}{\pi_{\text{ref}}(y_l | x)}\right]\right)$$

y_w is the winner (preferred), y_l is the loser (rejected). The loss is just binary cross-entropy: increase the log-ratio of preferred to reference for winners, decrease it for losers. β controls how strongly the model deviates from the reference policy.

Why DPO is simpler:

  • No reward model to train.
  • No value model.
  • No RL loop, just a supervised loss on preference pairs.
  • Empirically, implicit reward modelling often beats explicit modelling.

DPO works for aligning modalities (used in hallucination-aware DPO in MRAG evaluation) and reducing hallucination. It is attractive for reasoning alignment because reasoning quality is often easier to compare than to score. Preference pairs can compare correct versus incorrect reasoning, grounded versus hallucinated reasoning, safe versus unsafe tool use.

Limits of DPO: depends heavily on preference data quality, offline pairs do not encourage exploration, and it is hard for long-horizon agent tasks such as web browsing, code editing, robotics, and multi-step tool use.

EXPERTWhat is GRPO and how does it improve on PPO for reasoning tasks?

GRPO (Group Relative Policy Optimization) is the algorithm that powered DeepSeek-R1-Zero. It builds on PPO but removes the value model.

The motivation. Reasoning tasks naturally allow multiple attempts for the same prompt. Self-consistency samples multiple greedy paths and votes. Tree of Thoughts explores multiple branches. If the model can produce multiple candidate responses cheaply, we should use them to estimate advantage, instead of relying on a separately trained value model that predicts expected future reward.

The GRPO recipe:

  1. For each prompt q, sample G responses (a "group") from the current policy: o_1, o_2, ..., o_G.
  2. Score each response with a reward function: r_1, r_2, ..., r_G.
  3. Compute the group-relative advantage by normalising within the group:
$$A_i = \frac{r_i - \operatorname{mean}(r_1, \ldots, r_G)}{\operatorname{std}(r_1, \ldots, r_G)}$$
  1. Update the policy using a PPO-like clipped objective with this advantage, plus a KL term against the reference model.

Why this works without a value model. The advantage of action o_i is "how much better than expected was it?" In standard PPO, you train a value model V(s) to predict expected reward. In GRPO, you estimate expected reward by averaging over the sampled group. Group computation decides advantage of one response based on the others in the group.

The value model is removed because it is expensive to evaluate multiple actions at every state, and unnecessary when you can sample a group cheaply.

Reward modelling in GRPO is rule-based. Two types:

  • Accuracy rewards: enforce correct responses (math problems get rewards if the final answer is correct, code problems get rewards if it passes test cases). Cheap and objective.
  • Format rewards: enforce a thinking format. The model must put its reasoning between <think> and </think> tags. Gives a small reward when the format is respected.

DeepSeek-R1-Zero trained reasoning from pure RL using GRPO (no SFT warm-up) and surpassed OpenAI-o1 on reasoning benchmarks. This was a striking demonstration that you can elicit strong reasoning purely through reinforcement learning with simple rule-based rewards, no human preferences or value models required.

For agents specifically, GRPO can train by sampling multiple actions or responses for the same task, scoring them with rewards, and increasing the probability of better outputs. The agent learns from relative performance within the group instead of relying on a value model. This is particularly useful for tasks where the success criterion is checkable (the agent either solved the problem or did not).

INTERMEDIATEWhat is MCP, and what does it do (and not do)?

MCP stands for Model Context Protocol. It is a standard for how tools and data plug into agents. Before MCP, function calling connected one model to one tool. Each integration had a different API schema, authentication method, permission model, and response format. Adding a new tool meant writing yet another integration. This does not scale across many models and many tools.

MCP standardises the interface. Its architecture has three components:

  • Host: the AI application (Claude Desktop, Cursor, your custom agent).
  • Client: a connection manager inside the host that speaks the MCP protocol.
  • Servers: separate processes that expose tools, resources, and prompts via MCP. A server can be for a database, a file system, an IDE, a calendar, a maps service, or any productivity tool.

This makes tool capabilities reusable across agent clients. Write one Google Drive MCP server and it works with Claude, GPT, and any other MCP-compatible agent.

What MCP helps with:

  • Exposing tools through a standard schema.
  • Discovering capabilities at runtime (the agent can ask "what can you do?").
  • Passing structured arguments and returning structured results.
  • Reusing tools across hosts.

What MCP does not do:

  • Decide which tool to use next.
  • Decide whether the result is enough.
  • Decide whether to retry on failure.
  • Decide how to branch in the agent's workflow.
  • Store state across calls.
  • Recover from failure.
  • Synthesise the final answer from multiple tool calls.

Those decisions are the responsibility of the agent framework that sits above MCP. LangGraph, AutoGen, and similar frameworks handle the workflow logic. MCP is the plumbing, not the brain.

INTERMEDIATEHow does LangGraph structure agent workflows, and what are the common patterns?

LangGraph represents an agent workflow as a graph with four primitives:

  • State: stores current task information. The state is updated as the workflow progresses. Think of it as a shared blackboard.
  • Nodes: perform work (run an LLM call, call a tool, transform data) and update state.
  • Edges: determine which node runs next. Static edges are fixed transitions.
  • Conditional edges: dynamic routing based on state. The current node can decide which node runs next.

Common workflow patterns built on these primitives:

  • Prompt chain: a sequence of LLM calls where the output of one becomes the input of the next. Simple and linear.
  • Parallel processing: run multiple LLM calls in parallel and combine results. Good for embarrassingly parallel tasks such as scoring multiple candidates or applying multiple analyses to the same input.
  • Orchestrator-worker: an orchestrator breaks tasks into subtasks, delegates each to a worker, and synthesises the worker outputs. Provides more flexibility than parallel processing because subtasks can be dynamically defined.
  • Evaluator-optimizer: one agent generates a candidate, another evaluates it against success criteria, and conditional edges route back to the generator if the result is unsatisfactory. Useful for iterative refinement.

The Send primitive dynamically dispatches subtasks. For example, Send("llm_call", {"section": "Introduction"}) creates a new branch of work for the LLM to handle the Introduction section. Conditional edges enable loops such as "if missing info, search again".

The agent framework is essentially a state machine over LLM calls and tool calls. LangGraph makes this explicit and visual. The benefit is that you can reason about the workflow as a graph, debug it node by node, and add structured outputs to enforce schemas at each step.

Practical examples include: a research agent that searches, summarises, and writes a report; a coding agent that plans, edits, runs tests, and iterates; a customer support agent that classifies queries, routes to specialised sub-agents, and escalates when necessary.

Parameter-Efficient Fine-Tuning (PEFT)

BEGINNERWhat is PEFT and why do we need it?

Supervised Fine-Tuning (SFT) adapts a pretrained LLM by optimising it on instruction-response examples. Full SFT updates the entire model: all attention matrices, all MLP layers, every parameter. The mathematical view is W' = W_0 + ΔW where ΔW is what training learns and most of ΔW is trainable.

This becomes increasingly expensive as LLMs scale. For perspective: GPT-3 175B used several thousand petaflop/s-days to train. BLOOM 176B used 1.08M GPU hours on A100 80GB GPUs over 118 days. Llama 3.1 405B used over 16,000 H100 GPUs on 15T tokens. DeepSeek-V3 (671B total, 37B activated, MoE) cost roughly 2.788M H800 GPU hours and about 5.5 million dollars.

Three bottlenecks of full SFT:

  1. High training cost. Updating all parameters needs huge GPU memory, compute, and training time.
  2. Poor multi-task scalability. Each task or domain needs a separate full-size checkpoint. Ten tasks on a 70B model means 700B of weights to store, deploy, and maintain.
  3. Forgetting and overspecialisation. Narrow SFT shifts shared parameters toward the new data distribution. The target task improves, but broad capabilities and safety alignment may degrade. This is called catastrophic forgetting.

PEFT (Parameter-Efficient Fine-Tuning) is a family of methods that adapt a pretrained model by freezing most of the backbone and training only a small number of additional or selected parameters. The goal is to retain most of the performance of full SFT while reducing training cost, storage, and deployment cost.

Three main families based on where trainable parameters are added:

  • Prompt-based PEFT: learnable virtual tokens (soft prompts) at the input embedding or as prefix positions.
  • Adapter-based PEFT: small bottleneck neural modules inserted inside Transformer blocks.
  • LoRA-family PEFT: low-rank weight updates applied to attention or linear projection matrices.
INTERMEDIATEWhat is the difference between a text prompt and a soft prompt, and how does prompt tuning work?

A text prompt is a human-written task instruction or context. It gets tokenised into discrete text tokens before entering the LLM. Text prompts are readable by humans but not trainable: you cannot do gradient descent on text tokens because they are discrete.

A soft prompt (learnable prompt) is a small set of trainable virtual token embeddings. They live in the same embedding space as actual word tokens, but they do not correspond to any real word. They are optimised by gradient descent on the downstream task.

Text prompt: readable, not trainable. Soft prompt: trainable, not readable.

Prompt tuning is the simplest prompt-based PEFT method. Procedure:

  1. Freeze the pretrained LLM completely.
  2. Prepend a short sequence of trainable virtual token embeddings (say 20 to 100 tokens) to the input embeddings.
  3. Train only these prompt embeddings on downstream data using next-token prediction or task-specific loss.
  4. All LLM weights stay frozen throughout training.

The number of trainable parameters is tiny: 100 tokens × 4096 dim = 400K parameters, compared to billions in the model. The soft prompt acts as a learned context that conditions the frozen model.

An important property: prompt tuning becomes stronger as model size increases. The gap to full fine-tuning narrows as the base model gets larger. At very large scale, on some tasks and model families, prompt tuning can approach full model tuning while training orders of magnitude fewer parameters. At smaller model scales, the gap is larger because the frozen base is less capable.

P-tuning and P-tuning V2 extend this idea. P-tuning learns continuous prompts, optionally generated by a small prompt encoder (rather than directly learned). P-tuning V2 (deep prompt tuning) adds trainable prompts not only at the input but at every Transformer layer as layer-wise prefixes. The key change is from input-only soft prompts to layer-wise prompt parameters. P-tuning V2 closes much of the remaining gap between prompt tuning and full fine-tuning.

INTERMEDIATEHow do adapter-based PEFT methods work, and what is AdapterFusion?

Adapter-based PEFT inserts small trainable modules into a frozen Transformer. The backbone stays frozen, only the adapter modules are trained.

The Houlsby Adapter is the canonical design. After (or alongside) each attention or FFN sublayer, insert a bottleneck module: down-project to a small dimension, apply non-linearity, up-project back to the original dimension, then add a residual connection. The formula:

$$h' = h + W_{\text{up}}\,\sigma(W_{\text{down}}\,h)$$

The bottleneck dimension is small (often 16, 64), so the parameter count is much smaller than the surrounding Transformer layers. Training only updates W_down, W_up, and the LayerNorm if any.

Houlsby et al. showed that adapters achieve strong performance with far fewer parameters than fine-tuning the upper layers of a model. They work because the adapter sits in the residual path: the original output passes through unchanged plus a small learned correction.

AdapterFusion. A single adapter is modular but isolated. If you have many adapters trained on different tasks, useful knowledge across tasks is not automatically combined. A biomedical QA task might benefit from both a medical adapter and a QA adapter, but using them separately misses this synergy.

AdapterFusion has a two-stage workflow:

  1. Stage 1: Knowledge extraction. Train one adapter per source task with the backbone frozen. Each adapter learns task-specific knowledge in isolation.
  2. Stage 2: Knowledge composition. Freeze the backbone and all source adapters. Add a trainable fusion layer (attention-based) that dynamically combines outputs from multiple adapters. Train only the fusion layer on the target task.

At inference, the fusion layer selects useful information from multiple adapters based on the input. The attention pattern in the fusion layer is interpretable: a fusion activation heatmap shows which target tasks rely on which source adapters. Bright entries indicate the fusion layer pulls strongly from that source adapter for the current target task.

The benefit of AdapterFusion is non-destructive composition: the source adapters are not modified, so you can keep adding new tasks without affecting old ones. The cost is that the fusion layer adds compute, and you still need to train one adapter per source task.

Modern PEFT has shifted away from classic adapters toward LoRA-family methods because LoRA is more efficient and mergeable. But adapter ideas live on in the form of LoRA composition (multi-adapter routing) and in research directions such as MeteoRA.

ADVANCEDExplain LoRA in detail, including how it works during training, at inference, and what its key hyperparameters do.

LoRA (Low-Rank Adaptation) is the practical default in modern PEFT. The core idea is that the update ΔW learned during fine-tuning often has low intrinsic rank, meaning it can be approximated by a product of two thin matrices.

Mathematically:

$$\text{Full fine-tuning:}\quad W' = W_0 + \Delta W$$
$$\text{LoRA:}\quad W' = W_0 + BA, \quad \text{rank}(BA) \le r$$

W_0 has shape (d × d) and stays frozen. A has shape (r × d) and B has shape (d × r), with r much smaller than d. Together BA reconstructs a d × d update with at most r non-zero singular values. Only A and B are trainable.

Concrete example. For an 8.56B parameter model, you might use r = 16 LoRA on the attention projections of every layer. The total trainable parameter count comes out around 22.1M, less than 0.3 percent of the full model. The rest stays frozen.

Forward pass during training. The output uses two paths:

$$h = Wx + BAx = (W + BA)\,x$$

You compute Wx through the frozen weight and BAx through the LoRA branch, then add them. LoRA usually scales the BA branch by α/r where α is a hyperparameter, so the effective output is Wx + (α/r) · BA · x.

Backward pass. Gradients only flow into A and B. W stays frozen, so the memory cost of storing gradients and optimizer state is much smaller than full fine-tuning.

Inference time merging. Before deployment, you can merge the LoRA update into the base weight:

$$W' = W_0 + BA$$

After merging, you use a single adapted weight matrix W' with no separate LoRA branch. Inference latency is identical to the base model. This is a major engineering advantage compared to adapters, which add forward modules that increase latency.

Where LoRA is inserted. The original paper applied LoRA mainly to attention projection matrices (q_proj, k_proj, v_proj, o_proj). Modern fine-tuning often extends LoRA to more linear layers including MLP layers (gate_proj, up_proj, down_proj) for stronger adaptation. The trade-off is that attention-only is cheaper but covers less of the model.

Hyperparameters:

  • Rank r: capacity of the LoRA update. Typical: 8, 16, 32, 64. Higher rank means stronger adaptation but more trainable parameters and more memory.
  • LoRA alpha: strength of the LoRA update. Same as rank or about 2× rank. Controls how much the LoRA branch influences the base model. The effective scale is α/r.
  • Target modules: which linear layers receive LoRA. q_proj, k_proj, v_proj, o_proj are standard. Adding MLP layers is heavier but usually stronger.
  • LoRA dropout: regularisation on the LoRA branch. 0 to 0.1. Often 0 for large clean datasets, useful for small datasets to reduce overfitting.

The LoRA paper reports that on GPT-3 175B, LoRA matches or exceeds full fine-tuning on three datasets while training only millions of parameters. Increasing rank improves capacity, but gains saturate after a point. Studies on singular vector overlap show the top directions learned by rank-8 and rank-64 adaptations are highly similar, which supports the claim that useful updates concentrate in a low-dimensional subspace.

ADVANCEDWhat are QLoRA and DoRA, and how do they improve on LoRA?

QLoRA (Quantised LoRA) tackles the memory cost of holding the base model in GPU memory during fine-tuning. The frozen backbone is quantised to 4-bit precision (NormalFloat 4-bit, NF4), and LoRA adapters stay at higher precision (BF16 or FP16). Only A and B are trainable.

Memory comparison for a 65B model:

  • 16-bit (BF16 or FP16): about 130 GB.
  • 8-bit: about 65 GB.
  • 4-bit (QLoRA): about 32.5 GB.

This lets you fine-tune a 65B model on a single 48 GB GPU, which would otherwise require multiple GPUs. The quantisation introduces approximation error but largely preserves 16-bit fine-tuning performance because the LoRA adapters compensate for the precision loss. QLoRA results are typically within 1-2 percent of full BF16 LoRA on standard benchmarks.

QLoRA also uses double quantisation (quantising the quantisation constants) and paged optimizers to handle memory spikes during backprop. The combination makes 4-bit fine-tuning practical and reliable.

DoRA (Weight-Decomposed Low-Rank Adaptation) decomposes the weight matrix into two quantities and treats them separately:

  • Magnitude: how large each column vector of W is.
  • Direction: the unit vector pointing in each column's direction.

DoRA learns magnitude m directly as a separate trainable scalar per column, and updates direction via LoRA. The adapted weight is the learned magnitude times the normalised updated direction. Mathematically, full fine-tuning changes both magnitude and direction simultaneously. LoRA changes both through one low-rank ΔW, so the changes are entangled.

By separating magnitude and direction, DoRA's update behaviour gets closer to full fine-tuning. Empirically, DoRA outperforms LoRA, especially at low ranks. At r = 4 or r = 8, DoRA gives large accuracy gains over LoRA. The gap shrinks at higher ranks because LoRA's expressive power grows.

DoRA is more expensive than LoRA in compute because of the magnitude-direction decomposition, but the parameter count is similar. It is a drop-in replacement when you want to push parameter efficiency further or are constrained to very low ranks.

Why LoRA-family became the default:

  1. LoRA directly approximates full fine-tuning in weight space. Prompt tuning changes conditioning, adapters add transformations, but LoRA directly parameterises an additive update to existing weight matrices.
  2. Low-rank updates are often enough. Useful adaptations concentrate in a small subspace.
  3. Engineering advantages: small checkpoints (save only A and B), mergeable for inference (no latency penalty), multi-adapter serving (one base model serves many LoRA adapters at runtime), quantisation-friendly (QLoRA), and supported by mainstream tooling (Hugging Face PEFT, bitsandbytes, vLLM).

Recent 2025+ directions explore more expressive updates (HiRA, RaSA reduce the rank bottleneck), safety-preserving adaptation (SaLoRA fine-tunes while reducing damage to safety alignment), and multi-adapter composition (MeteoRA routes among multiple LoRA adapters). These are research directions, not yet as standardised as LoRA and QLoRA.

Cross-Topic Synthesis

EXPERTHow does the Transformer architecture appear across all the topics in this course?

The Transformer is the unifying architecture across the entire course. Every topic builds on or modifies it.

Topic 1 (Embedding). The vanilla Transformer with tokenization, positional encoding, and self-attention is introduced. KV cache makes autoregressive decoding efficient.

Topic 2 (Self-Supervised Embedding). Vision Transformer (ViT) applies the architecture to images by patchifying. MAE uses a ViT encoder for visible patches and a small ViT decoder for reconstruction. DINO uses two identical ViTs in a teacher-student setup.

Topic 3 (Alignment). CLIP has two Transformers (one for image, one for text) joined by a contrastive loss. CoCa adds a Transformer decoder for captioning. BLIP-2's Q-Former is a small Transformer that bridges frozen image and language encoders. LLaVA concatenates image features with text tokens and feeds them into a Transformer LLM.

Topic 4 (MLLM). LLaVA 1.5/Next, Qwen2-VL, and others are all Transformer-based MLLMs. The differences are in how images are tokenised (resolution handling, multi-tile, RoPE extensions). Janus-Pro shares a Transformer backbone between understanding and generation pipelines.

Topic 5 (Indexing). The vectors stored in vector databases come from Transformer-based encoders (text or image). The indexing structures (IVF, HNSW) do not change architecture, but they make Transformer embeddings searchable at scale.

Topic 6 (Token Reduction). All four methods (pruning, merging, routing, resampling) modify the Transformer's tokens to make self-attention cheaper. Information bottleneck theory unifies them.

Topic 7 (Multimodal RAG). The retrievers (text encoder, image encoder, ColPali) are Transformers. The generator (LLaVA, Qwen2-VL) is a Transformer-based MLLM. RAG is essentially Transformer-based encoders feeding into Transformer-based generators.

Topic 8 (RAG Evaluation). LLM-as-a-judge uses Transformers (GPT-4 or Claude) to evaluate other Transformer outputs. VCD modifies the Transformer's decoding to subtract noisy-image logits.

Topic 9 (Agents). The agent core is a Transformer. ReAct, CoT, ToT modify how we prompt the Transformer. RLHF, DPO, GRPO fine-tune the Transformer's weights to align with preferences.

Topic 10 (PEFT). LoRA modifies attention or linear projections inside the Transformer. Adapters insert modules between Transformer sublayers. Prompt tuning prepends soft prompts to the Transformer input.

The Transformer is universal because it is the simplest architecture that handles arbitrary token sequences with global context. Once you have one architecture that works for any modality you can tokenise, you can mix modalities, scale up, fine-tune cheaply, and build agents on top. This is the central insight of the course.

EXPERTHow do self-supervised learning, scaling laws, and emergent capabilities tie together with multimodal alignment?

This is the conceptual thread that runs through the first half of the course.

Step 1: scaling laws tell us that performance improves with model size N, data size D, and compute C, following power laws. To reduce error by a small amount, you typically need exponentially more compute. Despite diminishing returns, scaling unlocked emergent capabilities such as in-context learning and multi-step reasoning.

Step 2: scaling requires dense supervision. LLMs scaled effectively because every token is a learning signal. Vision struggled because labels are sparse (one per image). So we need denser learning signals for vision, which is exactly what self-supervised learning provides.

Step 3: SSL methods (rotation prediction, jigsaw, MAE, SimCLR, MoCo, DINO, I-JEPA) generate their own dense supervision from data. MAE gives dense per-patch reconstruction. Contrastive methods turn every image into a many-class classification by treating other batch members as negatives. DINO uses teacher-student with EMA targets.

Step 4: with strong SSL, vision encoders can be trained at scale, producing strong representations that are good for downstream tasks without lots of labels. This unlocked ViT scaling.

Step 5: now we have strong language encoders (from LLM scaling) and strong vision encoders (from SSL scaling). They speak different languages. Multimodal alignment is the bridge: contrastive image-text training (CLIP) projects both modalities into a shared embedding space. CLIP's training data is image-caption pairs scraped from the web, an enormous source of weak supervision.

Step 6: alignment unlocks zero-shot capabilities. CLIP can classify any new dataset by writing text prompts. CoCa adds generation. BLIP-2 connects frozen image and text models. LLaVA fine-tunes for instruction following on multimodal data. Modern MLLMs are descendants of these ideas.

Step 7: emergent capabilities in MLLMs include multimodal in-context learning, visual chain-of-thought reasoning, instruction following, and now even visual generation (unified models). These emerge because the model is large, trained on diverse multimodal data, and built on the shared-space foundation that alignment provides.

The thread: scaling demands dense supervision, SSL provides it for vision, alignment connects modalities, instruction tuning gives flexibility, and the result is models that exhibit increasingly general intelligence-like behaviour across modalities. Each step is a response to a limitation of the previous step.

EXPERTTrace one complete query through a modern MRAG system, showing how each course topic contributes.

Let us trace the query "what does the bar chart on page 3 of the climate report say about CO2 emissions in 2023?" through a modern MRAG system. Each step touches multiple course topics.

Ingestion (offline). The climate report PDF is ingested. Pages are kept as image screenshots (MRAG 2.0 approach). Each page screenshot is fed through PaliGemma (a Transformer-based VLM, Topic 1) fine-tuned via ColPali (Topic 7). The output is a sequence of patch embeddings per page (multi-vector representation). These embeddings are stored in a vector database (Topic 5) such as Milvus, indexed using HNSW or IVF. To save space, the embeddings could be quantised via Product Quantization.

Query encoding (online). The user query is tokenised using byte-level BPE (Topic 1) and embedded by ColPali's text encoder. Each query token becomes an embedding vector.

Retrieval (online). ANN search (Topic 5) finds candidate pages. With ColPali's late interaction (Topic 7), each query token finds its maximum-similarity match across all page tokens, summed for a final score. The top-k pages are returned. The system may also run BM25 (Topic 7) in parallel for exact term matching (in case "CO2" or "2023" need exact match), and combine with Reciprocal Rank Fusion (Topic 7).

Reranking. A cross-encoder reranker (Topic 7) re-scores the top 20 candidates with full query-page interaction. The top 5 reranked pages are kept.

Generation. The MLLM (Topic 4) such as Qwen2-VL or LLaVA-Next ingests the query plus the top 5 page images. The image encoder (Topic 2, Vision Transformer) extracts patch features. Token reduction (Topic 6) may be applied to compress the image tokens, since 5 page images at high resolution could blow the context budget. M-RoPE (Topic 4) handles variable-resolution inputs.

Reasoning. The MLLM produces an answer, ideally using chain-of-thought (Topic 4 and 9) to walk through what the bar chart shows. If the system is agentic (Topic 9), it might use ReAct: think about which page to focus on, possibly zoom in (Zoom-Refine from Topic 4) to read small numbers on the chart, then synthesise an answer.

Evaluation (offline or online). The RAG Triad (Topic 8) checks: context relevance (did we retrieve the right pages?), answer relevance (does the answer address the question?), and faithfulness/groundedness (are the claims supported by what is actually in the chart?). For multimodal specifically, query grounding (Topic 8) checks visual claims. If hallucinations appear, VCD (Topic 8) or DPO-based mitigation (Topic 9) could improve grounding.

Model adaptation. The MLLM was originally trained at general scale. To improve domain-specific performance on climate documents, the model could be adapted using LoRA (Topic 10) on a small instruction-following dataset of climate-related Q&A pairs. QLoRA (Topic 10) lets you fine-tune on a single GPU. The adapter is small enough to deploy as a separate file alongside the base model.

One query, ten topics. The system is a stack where the Transformer architecture is the backbone, SSL gives the embeddings, alignment connects modalities, indexing makes search fast, token reduction makes inference feasible, RAG retrieves evidence, evaluation catches errors, agentic loops add multi-step reasoning, and PEFT adapts the system to your domain. Every step builds on the previous topics.
